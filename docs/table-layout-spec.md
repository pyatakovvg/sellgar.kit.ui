# Техническое задание на архитектуру и геометрию компонента Table

- Статус: проект ТЗ. Требования из обсуждения сведены в единый контракт; нерешённые случаи перечислены в разделе 12.
- Дата: 2026-11-06.
- Обновлено: 2026-11-08.
- Пакет: `@sellgar/kit`.
- Целевой репозиторий: `frontend/sellgar.ui.admin/library/sellgar.kit.ui`.
- Область: архитектура core/runtime/view, расчёт колонок, токены размеров, ручной resize, программное закрепление хедера, закрепление колонок и виртуализация.

Таблица должна автоматически заполнять доступную ширину и поддерживать предсказуемое изменение колонок мышью. У обычной колонки базовый resize правосторонний. Закреплённые области имеют отдельный контекст независимого изменения ширин с общим ограничением обеих сторон. Расположение ручек должно соответствовать движущейся границе; согласование с прежним уточнением сторон описано в 9.4.3 и O7. Ограничения содержимого и выбранные пользователем размеры определяют момент появления горизонтального переполнения.

ТЗ сохраняет публичный API и React-представление. Внутренняя архитектура разделяется на core, runtime и view. Колонки размещаются через CSS Grid по рассчитанному шаблону с токенами `--numbers-X`; закреплением хедера управляет runtime на основе расчётов core. Выбор D3, другой библиотеки, worker или GPU не является требованием.

## 1. Объём работ

### 1.1. Входит в будущую реализацию

1. Собственная координатная модель строк и колонок.
2. Начальная автоматическая раскладка с фиксированными и auto-колонками.
3. Реакция на изменение ширины контейнера.
4. Ручное расширение и сужение колонок с правой стороны.
5. Контентные ограничения, `minWidth`, `maxWidth` и горизонтальное переполнение.
6. Сохранение корректной геометрии после завершения resize.
7. Виртуализация строк и колонок при сохранении React-содержимого ячеек, с динамическими высотами строк, измерениями и корректировкой позиции скролла.
8. Проверка совместимости существующих сценариев Table: заголовков, закрепления, selection, sort, tree, expansion, empty state и взаимодействий со строками.
9. Разделение правил, состояния работающей таблицы и React-представления между core/runtime/view.
10. Программное закрепление хедера относительно выбранного scroll-контейнера с учётом границ таблицы и горизонтального скролла.
11. Закрепление колонок через существующие `pinLeft`/`pinRight`, согласованное с общей раскладкой, resize, виртуализацией и вложенными таблицами. Проект контракта — раздел 9.4; решения O7–O8 требуют согласования до реализации соответствующего поведения.

### 1.2. Ограничения реализации

- Существующая внутренняя архитектура Table не является обязательной основой.
- Не использовать HTML table или CSS table layout как механизм геометрии таблицы.
- Использовать CSS Grid для размещения колонок по автоматически сформированному `grid-template-columns`. Размеры колонок определяет модель; CSS Grid получает результат расчёта, а не становится владельцем правил auto/fixed, resize и компенсации.
- Размеры в CSS-шаблоне передавать через токены `--numbers-X`. Прямая сериализация расчётной ширины как `${width}px` не соответствует контракту кита.
- Для закрепления хедера использовать программное управление. `position: sticky` не является механизмом его закрепления; CSS применяется для отображения рассчитанного положения.
- CSS продолжает использоваться для оформления, позиционирования рассчитанных элементов и внутреннего устройства React-содержимого ячеек.
- React остаётся renderer содержимого. Переписывание произвольного JSX в графические команды Canvas/WebGL не входит в задачу.
- Существующие публичные imports, compound API, render scopes и callbacks должны сохранять совместимость. По уточнению пользователя Column принимает `resizable?: boolean`: resize выключен по умолчанию и включается только через `resizable={true}` для конкретной колонки.
- Конфигурация без видимой auto-колонки является ошибочной. Нельзя молча преобразовывать произвольно выбранную fixed-колонку в auto.
- Worker и GPU допустимы только при обоснованной необходимости. Они не должны менять результаты геометрии и контракт взаимодействий.

Подготовка этого ТЗ не включает реализацию компонента, установку зависимостей, commit или push.

### 1.3. Границы core/runtime/view

| Слой    | Ответственность                                                                                                                                                                              |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Core    | Модель строк и колонок, правила auto/fixed, ограничения, расчёт геометрии и направленного resize, видимая область, расчёт ограниченного положения хедера                                     |
| Runtime | Состояние экземпляра таблицы, опорная раскладка, ручные запросы, активный drag, scroll owner и viewport, получение измерений, нормализация единиц, вызов core, публикация snapshots и команд |
| View    | Публичное React-представление, заголовки, строки, ячейки и controls; состав виртуального окна и CSS-оформление                                                                               |

Core получает обычные данные и состояние, возвращает результат вычисления. Он не зависит от React, DOM, observers, CSS Grid или способа отображения хедера. Браузерные измерения и подписки принадлежат runtime либо его платформенным адаптерам.

Математика обычных колонок и математика pin разделены внутри core. Обычный модуль отвечает за auto/fixed, base/manual, направленную компенсацию и overflow; модуль pin — за начальную pinWidth, независимый resize и общий бюджет обеих сторон. Согласующий расчёт передаёт обычной раскладке оставшуюся ширину центра и объединяет результаты в общую геометрию. Это не новый слой между core/runtime/view.

Runtime является владельцем текущего состояния работающей таблицы. View подписывается на его snapshots и передаёт команды; самостоятельный расчёт компенсации, опорных размеров или правил закрепления в React-компонентах недопустим.

```text
View: пользовательское действие
  -> Runtime: команда и актуальное состояние
  -> Core: расчёт следующего состояния и геометрии
  -> Runtime: публикация snapshot
  -> View: отображение рассчитанного результата
```

Названия слоёв не требуют создания отдельных публикуемых пакетов. Конкретное размещение файлов определяется при проектировании реализации с сохранением этих границ.

## 2. Термины и величины

Расчёты размеров и смещений выполняются в согласованных логических единицах шкалы `numbers`. Доступная ширина исключает внешние отступы и занятое вертикальным scrollbar пространство. Размер ячейки включает её внутренние отступы и границы по единой принятой box-модели.

Измерения DOM и координаты указателя поступают в браузерных CSS px. Runtime приводит их к логическим единицам перед расчётом. Число в имени `--numbers-600` нельзя безусловно считать равным 600 CSS px: адаптивная тема может задавать значение токена в `vw`.

При линейном масштабе шкалы:

```text
scale = фактическая длина одной единицы numbers в CSS px
logicalLength = measuredCssLength / scale
logicalPointerDelta = measuredCssPointerDelta / scale
```

Определять масштаб нужно по разрешённой браузером длине токена, а не через чтение числовой части строки с неизвестной единицей. Изменение масштаба темы требует обновить преобразование измерений и текущего drag без переписывания сохранённых логических запросов.

View автоматически строит шаблон из результата модели, например:

```css
grid-template-columns:
  var(--numbers-200)
  var(--numbers-600)
  var(--numbers-200);
```

Числовой трек в таком шаблоне не меняет семантический режим колонки: рассчитанная auto остаётся auto в модели. Сериализатор должен ссылаться на реально объявленные токены и учитывать формат дробных имён, например `--numbers-0_5`. Нельзя создавать ссылки на несуществующие токены или независимо округлять все колонки с потерей общей суммы ширин.

Числа в формулах и примерах далее обозначают логические единицы шкалы `numbers`.

| Обозначение        | Значение                                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| `W`                | Текущая доступная ширина контейнера                                                                 |
| `f[i]`             | Фактическая ширина fixed-колонки                                                                    |
| `F`                | Сумма `f[i]` всех активных fixed-колонок                                                            |
| `content[i]`       | Измеренная потребность содержимого колонки по выбранным правилам переноса и ограничения содержимого |
| `reference[i]`     | Ширина auto-колонки в опорной автоматической раскладке                                              |
| `floor[i]`         | Сохранённый нижний предел автоматического сжатия                                                    |
| `base[i]`          | Ширина auto-колонки без её ручного расширения в текущем состоянии раскладки                         |
| `manual[i]`        | Сохранённый запрос ручного расширения auto; может отсутствовать                                     |
| `width[i]`         | Фактическая ширина колонки                                                                          |
| `min[i]`, `max[i]` | Явные ограничения ширины; отсутствие максимума означает `+∞`                                        |
| `T`                | Суммарная ширина колонок                                                                            |
| `overflow`         | Величина горизонтального переполнения таблицы                                                       |

`reference`, `floor`, `base` и `manual` — разные величины. Изменение фактической ширины не означает автоматической записи нового пользовательского запроса.

`content[i]` не равняется длине строки или ширине только одного видимого body-cell. При выборе способа измерения необходимо учитывать заголовок, controls, отступы, шрифты и содержимое строк. Область измерений при виртуализации требует решения по пункту O4.

## 3. Инварианты

### 3.1. Размеры поверхности

- Контейнер Table занимает всю доступную ширину родителя.
- Высота определяется заголовком, данными, раскрытыми строками и остальными элементами Table. Фиксированная внутренняя высота и внутренний вертикальный viewport не должны быть обязательными.
- Добавление строк увеличивает логическую высоту. Виртуализация не должна требовать одновременного DOM-рендера всех строк.
- Строки могут иметь разную высоту, определяемую содержимым. Одинаковая или заранее фиксированная высота не является условием включения виртуализации.
- Сумма фактических ширин колонок всегда не меньше доступной ширины контейнера. Сужение останавливается на границе заполнения. Невыполнимая конфигурация верхних пределов отклоняется; свободный остаток справа не отображается.
- Если нижние ограничения не позволяют поместить колонки, появляется горизонтальное переполнение.

### 3.2. Типы колонок

- В непустой активной конфигурации должна оставаться хотя бы одна auto-колонка.
- Единственная колонка обязана быть auto.
- Из двух колонок fixed может быть максимум одна.
- Ручное расширение auto не преобразует её в fixed.
- Даже если вручную расширены все auto, их автоматическая база сохраняется.
- Схема без колонок или без видимой auto-колонки отклоняется как ошибочная. Пустой набор строк при корректной схеме отображает предусмотренное пустое состояние.

### 3.3. Содержимое и ограничения

- Для auto-колонок измеренная потребность содержимого повышает нижний предел независимо от первоначальной автоматической доли. Если сумма нижних пределов превышает доступную ширину, runtime увеличивает `T` и появляется горизонтальная прокрутка внутри таблицы.
- У auto-колонки явный `minWidth`, включая 0, не отключает измерение: результат не может быть ниже заданного минимума. При явном `maxWidth` измеренный контент не повышает предел сверх максимума; способ отображения оставшегося переполнения определяется контрактом ячейки.
- У auto-колонки явный `minWidth`, включая 0, является нижним пределом ручного resize независимо от измеренного содержимого. Без `minWidth` нижним пределом остаётся контентный floor. Ручной запрос сохраняется при новых измерениях, отмена восстанавливает прежнее состояние, reset возвращает автоматическую раскладку.
- Нижние и верхние ограничения применяются до фиксации результата resize.
- `min[i] > max[i]` является ошибкой конфигурации.
- При нехватке места нельзя получать отрицательные ширины.

## 4. Опорная раскладка и контентный предел

Опорная раскладка формируется при наличии измеримой доступной ширины. Нулевая ширина скрытого контейнера не должна становиться опорным размером.

Для auto-колонки нижний предел определяется следующим образом:

```text
floor[i] = max(min[i], min(content[i], max[i]))
```

Контентный минимум применяется только к auto-колонкам без явной числовой ширины. У fixed-колонок `width` ограничивается явными `min/max`; измерение содержимого не увеличивает ширину. Если `minWidth` отсутствует, нижний предел resize равен объявленному `width` после применения `maxWidth`. Явный `minWidth`, включая 0, заменяет этот минимум.

`reference[i]` предварительно должен удовлетворять явным `min/max`, но не ограничивает контентный минимум. При отсутствии явных ограничений `min[i] = 0`, `max[i] = +∞`. Browser измеряет смонтированные заголовки и ячейки с учётом padding и элементов управления; runtime накапливает максимальную потребность по колонке.

Пример: при `W = 1000`, `F = 400` единственная auto получает `reference = 600`.

| Потребность содержимого | reference | floor при отсутствии дополнительного min |
| ----------------------: | --------: | ---------------------------------------: |
|                     200 |       600 |                                      200 |
|                     600 |       600 |                                      600 |
|                     800 |       600 |                                      800 |

Последняя строка означает: колонка получает не менее 800 единиц шкалы `numbers`, хотя первоначальная доля была 600. При `F = 400` общая ширина равна 1200 и появляется горизонтальное переполнение 200. Последующее уменьшение контейнера не сжимает колонку ниже измеренного минимума.

Изменение окна само по себе не переписывает опорный размер, контентный предел или ручной запрос. Иначе расширение окна может необратимо повышать минимум, а сужение — стирать его.

Срок жизни опорной раскладки и её обновление при смене данных или схемы определяются в O2. До этого решения опорные размеры нельзя незаметно пересоздавать на каждом render, resize или mount виртуализированной ячейки.

## 5. Автоматическая раскладка при изменении контейнера

Этот раздел описывает автоматическую раскладку. Его формулы нельзя безусловно запускать вместо направленной операции ручного resize из раздела 7.

### 5.1. Единственная auto

Без верхнего ограничения:

```text
base  = max(floor, W - F)
width = max(base, manual), если manual есть
width = base, если manual отсутствует
T     = F + width
overflow = max(0, T - W)
```

При наличии совместимого верхнего ограничения:

```text
base  = clamp(W - F, floor, maxWidth)
width = min(maxWidth, max(base, manual)), если manual есть
```

Если `F + maxWidth < W`, заполнить контейнер при соблюдении максимума невозможно. Применяется решение O3, а не скрытое нарушение одного из ограничений.

### 5.2. Несколько auto

Ручные расширения не должны участвовать в расчёте автоматических долей других auto. Сначала вычисляются `base[i]`, затем накладываются `manual[i]`:

```text
width[i] = min(max[i], max(base[i], manual[i]))
```

Для отсутствующего `manual[i]` используется только `base[i]`.

Предлагаемый способ автоматического распределения:

```text
R = W - F
base[i] = clamp(lambda * weight[i], floor[i], max[i])
```

`lambda` подбирается так, чтобы сумма `base[i]` равнялась `R`, если ограничения это допускают. При равных весах колонки, не упёршиеся в ограничения, получают равные ширины.

Если `R < sum(floor[i])`, используются нижние пределы и возникает переполнение. Если `R > sum(max[i])`, совместное выполнение заполнения и верхних ограничений невозможно.

Равные веса являются предложением для распределения, а не уже согласованным публичным API. Выбор исходных долей фиксируется по O5.

### 5.3. Сохранение пользовательского запроса

При `F = 400`, `floor = 200`, `manual = 700`:

| Последовательность |    W | base | width | overflow |
| ------------------ | ---: | ---: | ----: | -------: |
| Исходный размер    | 1000 |  600 |   700 |      100 |
| Окно расширили     | 1200 |  800 |   800 |        0 |
| Окно вернули       | 1000 |  600 |   700 |      100 |
| Окно уменьшили     |  800 |  400 |   700 |      300 |

Автоматический рост фактической ширины до 800 не записывает `manual = 800`.

## 6. Ручное изменение auto

Правила этого раздела описывают базовый resize без pin. Для закреплённых областей и границ центра применяется 9.4.3; переносить эти правила на pin до завершения O7 нельзя.

- Ручка расположена справа.
- Левая граница активной auto неподвижна; правая следует за указателем в пределах допустимого диапазона.
- Ручное сужение не должно уменьшать колонку ниже её собственной текущей автоматической ширины `base`.
- Ни расширение, ни обратное сужение ручного расширения auto не должны перераспределять ширины других auto.
- Если таблица заполняла контейнер, расширение auto сверх `base` увеличивает `T` и создаёт горизонтальное переполнение.
- Колонки справа сдвигаются вслед за новой правой границей; их ширины остаются прежними.

Для неизменного контейнера во время операции:

```text
target = clamp(widthAtDragStart + pointerDeltaX, base, maxWidth)
```

Требуемый переход состояния при явном ручном возврате к автоматической границе:

```text
если target достиг base:
    удалить manual
иначе:
    manual = target
```

Это правило снимает пользовательское расширение. Сохранение самого `base` в `manual` создало бы ложный минимум после следующего уменьшения окна. Простое нажатие без перетаскивания не должно сбрасывать настройку.

Если окно расширилось так, что `base >= manual`, запрос сохраняется до явного ручного возврата или отдельной операции сброса. Само изменение окна его не удаляет.

## 7. Направленный resize fixed с правой стороны

Resize доступен только для колонки с явным `resizable={true}`. Отсутствующее значение и `false` запрещают захват и скрывают ручку. Без pin у последней активной колонки разрешение игнорируется при любом значении. При наличии pin границы контекстов задаются 9.4.3 и O7.

### 7.1. Общие правила

Правила этого раздела описывают базовый resize без pin. При наличии закреплённых областей нельзя автоматически включать pin в общий набор компенсации или определять крайнюю колонку по всей схеме: контексты задаются 9.4.3 и O7. Общие инварианты min/max, сохранения запросов и заполнения таблицы действуют и для будущей реализации pin.

1. Ручка находится справа от изменяемого столбца.
2. Левая граница активного столбца остаётся на месте.
3. Правая граница следует за указателем до достижения допустимых ограничений.
4. Ширины и координаты колонок слева не меняются из-за этого drag.
5. Компенсировать изменение ширины могут только auto-колонки справа от активного столбца.
6. Fixed-колонки справа сохраняют ширины и сдвигаются при необходимости.
7. После отпускания указателя геометрия не должна перескакивать вследствие повторного глобального распределения.

### 7.2. Расширение

Пусть `d >= 0` — допустимое увеличение active fixed. Для каждого auto справа существует доступный запас сжатия до его действующего нижнего ограничения. Если у него есть ручной запрос, компенсация не должна стирать этот запрос или сжимать колонку ниже него.

Для состояния без незаполненной области:

```text
Cright = суммарный допустимый запас сжатия auto справа
compensation = min(d, Cright)
Tnew = Told + d - compensation
```

Распределение компенсации между несколькими auto справа должно использовать выбранную политику долей и ограничения каждой колонки. Auto слева в эту сумму не входят.

Когда запас справа исчерпан, дальнейшее увеличение активной колонки увеличивает `T` и горизонтальное переполнение.

### 7.3. Последний столбец

Без pin у крайнего правого столбца всей активной схемы нет ручки resize. При наличии pin крайние границы определяются внутри обычной области, отдельно от закреплённых: справа перед правым pin и слева рядом с левым pin. Устройство resize закреплённых областей описано в 9.4.3 и O7. Граница логического контекста не зависит от того, какие колонки сейчас смонтированы виртуализацией.

Остальные ручки содержат два независимых индикатора: левый и правый. Зелёный показывает разрешённое движение в свою сторону, серый — достигнутый предел. Состояние индикатора рассчитывается из тех же ограничений, что и операция resize, и обновляется во время drag и изменения контейнера.

Прежний сценарий прямого resize последней fixed отменён этим уточнением пользователя.

### 7.4. Обратное сужение fixed

Если справа есть auto, освободившееся пространство может заполняться ими в пределах ограничений. Сначала должно уменьшаться существующее переполнение; расширение auto для заполнения требуется только при появлении незанятого места.

Для допустимого отрицательного изменения `d`:

```text
TwithoutCompensation = Told + d
requiredFill = max(0, W - TwithoutCompensation)
growth = min(requiredFill, доступный запас расширения auto справа)
Tnew = TwithoutCompensation + growth
```

Сужение ограничивается существующим overflow и запасом расширения auto справа. Если они исчерпаны, активная граница останавливается. Результат `Tnew < W` запрещён.

### 7.5. Состояние после drag

Для направленного resize недостаточно сохранить только новую fixed-ширину и заново применить формулу `W - F` ко всем auto: это может изменить колонки слева и отменить результат операции.

Результат направленной раскладки должен быть представлен в состоянии движка. Способ его хранения не предписывается. Переход к последующему resize контейнера необходимо определить по O6 и проверить отдельной последовательностью событий.

## 8. Изменение контейнера и жизненный цикл операции

- Resize контейнера является отдельной операцией и может перераспределять автоматические ширины по всей таблице.
- Он не должен автоматически переписывать пользовательские запросы, опорные размеры и контентные пределы.
- При изменении контейнера во время drag границы и точка отсчёта указателя пересчитываются без скачка.
- Обработка горизонтального скролла во время drag должна использовать координаты содержимого, а не смешивать их с координатами окна.
- При достижении min/max разделитель останавливается на границе. Начальная точка захвата не переносится в место разворота курсора: изменение возобновляется только после возвращения указателя к соответствующей точке на остановившейся ручке. Нейтральные обновления не сбрасывают эту опору.
- Отмена операции восстанавливает её пользовательские изменения, сохраняя актуальную внешнюю ширину контейнера.
- Обновление данных или схемы во время drag должно иметь явную политику продолжения либо отмены операции.

## 9. Координаты, виртуализация и программное закрепление хедера

### 9.1. Общая геометрия

Геометрия является общей для заголовка, body, закреплённых областей и служебных строк.

Для обычного порядка колонок:

```text
x[0] = 0
x[i] = sum(width[j]), где j < i
T = sum(width[i])
overflow = max(0, T - W)
```

Для строк:

```text
y[row] = headerHeight + сумма высот предшествующих строк
contentHeight = headerHeight + сумма высот всех логических строк
```

Высота поверхности дополнительно учитывает её отступы, границы и место scrollbar, если он участвует в потоке. Изменение ширины может менять переносы содержимого и высоты строк.

### 9.2. Виртуализация

Виртуализация должна:

- Отбирать видимые строки и колонки по общей геометрии и viewport с overscan.
- Работать при внешнем вертикальном скролле и естественной высоте таблицы.
- Сохранять логические размеры не отрисованных областей.
- Не сбрасывать размеры и пользовательские запросы при unmount ячеек.
- Не требовать знания ширины через измерение каждого DOM-cell на каждом scroll.
- Поддерживать реальные высоты раскрытых и многострочных строк через оценки для неизмеренных областей, фактические измерения и последующую корректировку геометрии и скролла.
- Сохранять соответствие header/body и корректность закрепления при resize.

Фиксированные или известные заранее высоты допускаются как частный упрощённый режим. Основной контракт не должен требовать их от потребителя.

#### 9.2.1. Оценки и измерения высот

Для каждой логической строки используется актуальная измеренная высота либо оценка:

```text
height[i] = measuredHeight[i], если измерение актуально
height[i] = estimatedHeight[i], если актуального измерения нет

offset[0] = 0
offset[i] = sum(height[j]), где j < i
bodyHeight = sum(height[i])
```

По накопленным высотам core определяет диапазон строк, пересекающий viewport и overscan. Верхняя и нижняя пустые области либо другой выбранный механизм размещения сохраняют полную текущую логическую высоту body, включая не отрисованные строки.

После отображения runtime получает фактические размеры и приводит их из CSS px к единицам `numbers`. Изменения размеров вследствие переносов, изображений, асинхронного содержимого или шрифтов должны повторно обновлять измерение.

Измерения хранятся по стабильной identity логической строки и версии геометрии/содержимого. Индекс строки в текущем массиве не является достаточным ключом. Выход строки из DOM не должен удалять её актуальное измерение.

При изменении ширин колонок, содержимого или типографики затронутые измерения признаются устаревшими. Повторное измерение не должно блокировать отображение всей таблицы: до уточнения используется обозначенная как оценочная высота.

#### 9.2.2. Корректировка скролла по видимой строке

До применения пакета изменённых высот runtime определяет опорную видимую строку и положение viewport внутри неё. Overscan-строка выше видимой области не выбирается в качестве такой опоры. Учитываются перекрывающий закреплённый хедер и актуальные внешние отступы viewport.

После пересчёта core возвращает новую геометрию, а runtime корректирует выбранный scroll owner так, чтобы сохранить ту же видимую строку и смещение внутри неё. Для неизменного смещения внутри опорной строки:

```text
deltaScroll = newAnchorPosition - oldAnchorPosition
newScrollTop = oldScrollTop + deltaScroll
```

Позиции опоры и scroll должны быть выражены в одной системе координат. При записи в браузер логическая корректировка преобразуется в CSS px и ограничивается допустимым диапазоном scroll owner.

- Если изменилась высота строк выше опоры, корректируется scroll, чтобы видимое содержимое не сдвинулось.
- Изменение высот только ниже опоры само по себе не должно двигать viewport.
- Если изменилась сама опорная строка, сохраняется допустимое смещение внутри неё; оно не может указывать за её новую нижнюю границу.
- Если опорная строка удалена или скрыта, выбирается ближайшая сохранившаяся строка в прежнем порядке: сначала следующая, затем предыдущая; при отсутствии строк используется допустимое пустое состояние.
- Коррекция должна опираться на актуальный viewport и не возвращать пользователя к позиции, сохранённой до его нового действия прокрутки.
- Несколько измерений применяются согласованным пакетом, без последовательного видимого перемещения viewport после каждой ячейки.
- Нативное scroll anchoring и корректировка runtime должны быть согласованы, чтобы изменение высоты не компенсировалось дважды.
- Если таблица не участвует в видимой области, её корректировка не должна перехватывать прокрутку другого содержимого страницы.

Уточнение оценок может менять полную высоту таблицы и размер scrollbar. Гарантия сохранения видимого содержимого не означает, что точная полная высота известна до измерения всех необходимых областей.

#### 9.2.3. Совместная виртуализация строк и колонок

Высота строки зависит от её ячеек, включая колонки, которых сейчас нет в DOM. Нельзя объявлять измерение только видимых ячеек точным измерением всей строки.

Для актуальной версии ширин и содержимого необходимо сохранять уже известные высоты ячеек или эквивалентную информацию, достаточную для определения высоты строки. Горизонтальный unmount высокой ячейки не должен сам по себе уменьшать строку.

Если вновь отображённая колонка содержит более высокую ячейку, измерение уточняет высоту строки, после чего применяются общие правила пересчёта и сохранения опоры viewport. При неполном покрытии колонок высота остаётся уточняемой оценкой.

Инвалидация при реальном изменении содержимого или ширины должна позволять высоте уменьшаться. Запрет на уменьшение при одном только unmount не должен превращаться в пожизненное сохранение максимальной когда-либо наблюдавшейся высоты.

Header, body, закреплённые колонки и expanded lines используют согласованную высоту каждой логической строки. Программное закрепление хедера получает полную актуальную логическую высоту таблицы, а не границу последней смонтированной строки.

#### 9.2.4. Ответственность слоёв

- Core принимает текущие высоты и их изменения, рассчитывает накопленные координаты, видимый диапазон, размеры пропущенных областей и положение опорной строки.
- Runtime владеет измерениями и их актуальностью, viewport и опорой, получает изменения размеров, вызывает core и применяет согласованную корректировку scroll owner.
- View отображает выбранное окно строк и ячеек, сохраняет логическое место не отрисованных областей и предоставляет элементы для измерения. Требование одинаковой высоты не закладывается в React-представление.

Оценки высот не являются точными контентными пределами колонок и не должны автоматически переписывать `reference` или `floor` ширин. Правила измерения контентной ширины остаются предметом O4.

### 9.3. Программное закрепление хедера

Выбранный механизм — закрепление под управлением runtime. Поддерживаются обычное отображение без закрепления и программное закрепление относительно выбранного вертикального scroll owner. Для естественной высоты таблицы scroll owner может быть страницей либо внешней прокручиваемой панелью; внутренний viewport фиксированной высоты не является обязательным.

Runtime получает положение таблицы и хедера, высоту хедера, положение viewport и актуальный верхний отступ. Core получает эти данные в единой системе координат и определяет смещение. View применяет рассчитанное положение с использованием принятого контракта токенов.

Положение хедера ограничивается самой таблицей:

- До достижения порога хедер находится на обычном месте.
- При достижении порога хедер удерживается у верхнего края viewport с заданным отступом.
- При достижении конца таблицы хедер уходит вместе с ней и не остаётся поверх следующего содержимого страницы.
- Если высоты таблицы недостаточно для перемещения хедера, он не получает дополнительного свободного хода.

Для вертикального закрепления сверху после нормализации координат:

```text
headerTop = исходная позиция хедера в координатах содержимого scroll owner
tableBottom = нижняя граница таблицы в тех же координатах
scrollTop = положение вертикального scroll owner
topOffset = отступ от верхней границы его viewport
headerHeight = актуальная высота всего хедера

desiredShift = scrollTop + topOffset - headerTop
maxShift = max(0, tableBottom - headerTop - headerHeight)
headerShift = clamp(desiredShift, 0, maxShift)
renderedHeaderTop = headerTop + headerShift - scrollTop
```

`topOffset` может учитывать шапку приложения и другие закреплённые панели, в том числе при изменении их высоты. Механизм передачи этой величины должен сохранять совместимость публичного API; новые props здесь не назначаются.

Границы ответственности:

- Core рассчитывает смещение и состояние хедера: обычное, закреплённое или уходящее у конца таблицы.
- Runtime отслеживает выбранный scroll owner, scroll/resize и изменения размеров, нормализует измерения и обновляет snapshot. Получение геометрии не должно требовать чтения всех ячеек на каждом scroll.
- View применяет позицию, clipping и порядок наложения. Зависимости от DOM и конкретного способа позиционирования не попадают в core.

Header и body используют одну геометрию колонок и один рассчитанный шаблон. Горизонтальное положение хедера синхронизируется с body, включая виртуализированные и закреплённые колонки. Программное вертикальное закрепление не должно менять размеры колонок или создавать независимое состояние горизонтального скролла.

По согласованию с пользователем до порога хедер находится в нативном потоке поверхности. На время программного закрепления его стабильный контейнер выносится в локальный portal host Table вне scroll viewport. При возврате контейнер снова входит в обычный поток. React portal target остаётся постоянным, чтобы controls не перемонтировались. Исходное место хедера в вертикальной геометрии сохраняется, поэтому переход к закреплённому отображению не сдвигает строки. Высота хедера измеряется заново при переносах, нескольких уровнях заголовков или изменении controls.

Должен существовать единственный интерактивный React-хедер. Переходы между состояниями не должны терять фокус, локальное состояние controls, активную операцию resize или создавать вторую доступную для взаимодействия копию заголовков.

Программное смещение само по себе не отменяет clipping и stacking context предков. Если выбранная структура требует другого слоя размещения, view может использовать portal или отдельную поверхность. Это деталь размещения; расчёт core и состояние runtime от неё не зависят. Использование portal не отменяет требования к единственному хедеру и сохранению его состояния.

### 9.4. Закреплённые колонки: проект расширения

Статус: проект расширения по поручению пользователя от 2026-11-08. Реализованы отдельная математика бюджета (9.4.7), инициализация одного и набора pin (9.4.8–9.4.9) согласование геометрии с центром (9.4.10) и runtime (9.4.11); декларативный pin подключён к React-компоненту (9.4.12). Последнее уточнение пользователя: pin имеют собственную начальную ширину и независимо расширяются, не сжимая другие pin; их суммарная ширина с обеих сторон ограничена видимым контейнером за вычетом резерва центра, например --numbers-50. Это заменяет предположение о компенсации между pin. Прежние стороны ручек требуют повторного согласования с независимым изменением ширины — O7. Источники начальной ширины и распределение набора выбраны; для первого runtime принят упрощённый fallback при сужении контейнера (9.4.11).

#### 9.4.1. API, порядок и общая ширина

- Используются существующие `Column.pinLeft?: boolean` и `Column.pinRight?: boolean`; по умолчанию закрепления нет. Одновременно включать оба флага для одной колонки запрещено.
- Предлагаемый визуальный порядок: закреплённые слева, обычные, закреплённые справа. Внутри каждой группы сохраняется порядок, определённый `order`/исходной позицией. Скрытые колонки не участвуют. Этот порядок един для геометрии, DOM и `aria-colindex`; он сам по себе не задаёт общий для всех областей контекст resize.
- При переходе в pin начальная ширина определяется отдельно и ограничивается допустимым бюджетом; прежняя неограниченно увеличенная ручная ширина не переносится без проверки. Публичный режим auto/fixed не меняется молча. Предложение реализации: отдельное состояние pinWidth, чтобы инициализация pin не стирала обычные base/manual; выбор начальной ширины описан в 9.4.8, возврат из pin — O8. Отдельные экземпляры Table, scroller и состояния строк не создаются.
- Хотя бы одна видимая auto остаётся обязательной во всей схеме. Первый runtime требует auto в центре (9.4.11); схема только с fixed в центре отклоняется. Режим без auto в центре не реализуется созданием фиктивной колонки или сменой её режима.
- Resize остаётся opt-in для каждой колонки. При наличии pin нельзя применять прежний запрет последней колонки ко всему визуальному порядку. Пользователь определил крайние колонки обычного контекста у границ с pin; независимый resize pin ограничивается общим бюджетом, а стороны его ручек требуют завершения O7.
- Состояние и геометрия сопоставляются по columnId. Инициализация pinWidth не должна случайно переписывать обычные пользовательские запросы; политика их восстановления при снятии pin уточняется в O8. Простое изменение порядка не является основанием потерять сохранённые настройки.

#### 9.4.2. Расчёт экранного положения

Помимо ширины раскладки `W`, используется `V` — фактически доступная горизонтальная ширина viewport этой таблицы после clipping. Вложенная таблица может получить общую поверхность шире `V`; закреплять её колонки относительно полной выделенной поверхности неправильно.

Все величины ниже — логические единицы `numbers`; начало viewport принято за 0:

```text
s = смещение начала видимого viewport относительно содержимого таблицы
PL = сумма ширин pinLeft
PR = сумма ширин pinRight
VC = V - PL - PR
x[i] = сумма ширин колонок до i в общем визуальном порядке

displayX[i] = сумма ширин предшествующих pinLeft,             если pinLeft
displayX[i] = x[i] - s,                                    если обычная
displayX[i] = V - сумма ширин pinRight от i до конца группы, если pinRight

pinShift[i] = displayX[i] - (x[i] - s)
```

Закреплённые колонки остаются на своих сторонах с начала отображения, включая случай без overflow. Центр отображается и принимает pointer hit только внутри `[PL, V - PR]`; левая и правая области ограничены собственными прямоугольниками. Координаты одни и те же для Header и Body. Формулы предполагают допустимый размер закреплённых областей; случай `VC <= 0` нельзя решать взаимным перекрытием — см. O8.

Единый нативный horizontal scroll owner и системный Scrollbar сохраняются. В обычном невложенном случае длина прокрутки остаётся `max(0, T - V)`: длина центра `T - PL - PR` минус его viewport `V - PL - PR` даёт ту же разность. Во вложенных таблицах scrollLeft принадлежит общему владельцу, а `s` и `V` переводятся в локальные координаты; отдельные scroller и независимый scrollLeft не создаются.

#### 9.4.3. Независимый resize pin и общий бюджет

Pin не входят в общий контекст resize обычных колонок. Крайними в обычной области остаются колонка перед правым pin и первая обычная колонка рядом с левым pin; применять запрет последней колонки ко всему массиву L/C/R неправильно.

По последнему уточнению пользователя:

1. При закреплении определяется начальная ширина pin. Даже если раньше эта колонка была сильно расширена обычным resize, она должна войти в допустимый бюджет закреплённой области.
2. Каждый pin изменяет ширину независимо. Расширение одного pin не требует уменьшать другой pin на ту же дельту; суммарная ширина pin-группы не обязана оставаться прежней.
3. Левые и правые pin делят один бюджет видимой ширины. Ограничение справа обязательно учитывает уже занятое место слева, и наоборот.
4. Pin не должны образовывать прокручиваемую закреплённую область или выходить за доступную ширину. Для центра сохраняется резерв. Пользователь привёл --numbers-50 как пример; финальное значение и способ задания резерва пока не выбраны.
5. При достижении общего предела дальнейшее расширение активного pin прекращается. Другие pin автоматически не сжимаются, их сохранённые ширины не переписываются.

```text
V = видимая ширина контейнера Table, а не ширина растянутого содержимого
G = резерв центра в логических единицах numbers
PL = сумма фактических ширин всех левых pin
PR = сумма фактических ширин всех правых pin

PL + PR <= V - G
maxForPin[i] = min(maxWidth[i], V - G - сумма ширин всех остальных pin)
```

Пример: V=1000, G=50, PL=400, PR=200. Общий запас дальнейшего расширения любого pin равен350. Достигнув суммы950, pin сохраняют минимум50 видимой ширины центра. Этот запас общий, а не по350 отдельно для каждой стороны. `G=50` отображается через токен `--numbers-50`, не через литерал50px.

Если `maxForPin[i] < minWidth[i]` или не помещается сумма min новых pin, допустимого перехода нет. Нельзя решать конфликт отрицательной шириной, скрытым нарушением min/max или сжатием соседнего pin вопреки независимости. Начальное распределение нескольких pin описано в 9.4.9; внешнее сужение контейнера требует завершения O8.

**Положение ручек — открытое следствие O7.** Ранее пользователь указал у левых pin ручку слева, у правых — справа. Для независимого изменения ширины при закреплении внешнего края к viewport движущаяся граница обратная: у левого pin правая, у правого левая. Например, единственный левый pin занимает0..200; независимое расширение до250 даёт0..250, левая граница остаётся0. Чтобы сохранить связь ручки с мышью, нужно пересогласовать сторону ручки либо саму опорную геометрию; нельзя молча объявить прежнее сочетание реализуемым.

Общие требования к операции:

- Два индикатора и ArrowLeft/ArrowRight описывают физическое движение ручки. Shift сохраняет шаг10; обычный шаг1. Доступность учитывает min/max и общий остаток бюджета обеих сторон.
- У обычной колонки учитывается горизонтальный scroll: указатель переводится в координаты содержимого. У pin используется его экранная проекция: прокрутка центра при неподвижной мыши не меняет ширину pin.
- Масштаб темы и transform нормализуются браузерным адаптером. Смена масштаба/положения viewport согласованно обновляет рабочую опору; выход за min/max и разворот мыши её не переносят. Cancel сохраняет отдельный исходный снимок.
- Pin/order/visibility, меняющие контекст активной операции, сначала отменяют её, затем применяются одной транзакцией по columnId. Обычные обновления данных не отменяют drag без причины.
- Рост pin сокращает видимый viewport центра. Пересчёт обычных колонок под эту ширину — отдельный переход геометрии, а не компенсация другими pin. Ограничение PL+PR само по себе не доказывает отсутствие горизонтального overflow центра: если его fixed/min/manual не помещаются, это нужно явно согласовать с фразой «pin не могут создавать скролл», не нарушая прежних ограничений ширин.

#### 9.4.4. Виртуализация, состояния и вложенность

- Состав горизонтального окна: все закреплённые колонки плюс обычные колонки, пересекающие `[s + PL, s + V - PR]`, с overscan центра. Каждая ячейка рендерится один раз, пересечения наборов устраняются.
- Виртуализация строк остаётся общей. Высота строки определяется всеми её измеренными ячейками, включая закреплённые, и применяется одновременно во всех областях. Измерения не разделяются на три независимых кеша.
- Pin не клонирует строку, ячейки, Header или интерактивные controls. Сохраняются keys, focus, row handlers, Actions и локальное React-состояние. Скрытые за закреплёнными областями controls центра не должны оставаться недоступными для открытия с клавиатуры: фокусируемая ячейка доводится до видимости именно в viewport центра.
- Header до вертикального порога остаётся в потоке, при закреплении переносится прежним стабильным контейнером в локальный portal. Горизонтальные смещения применяются одинаково в обоих состояниях; существующий `-s` Header нельзя учесть второй раз.
- Закреплённый Body перекрывает только центр своей строки; Header — Body своей таблицы. Локальный stacking context таблицы сохраняется, pin не повышает её над Drawer, Popover или соседними таблицами. Требуются непрозрачные фоны, согласованные hover/разделители и прежний скруглённый контур.
- Expanded остаётся единым блоком. Вложенный Table использует собственную схему pin и границы пересечения своего контейнера с общим viewport. Pin родителя не наследуется колонками ребёнка; новых scroll owner и порталов в document.body не появляется.

#### 9.4.5. Предлагаемая реализация в текущей архитектуре

Проверено по source на 2026-11-08:

1. Configurator уже принимает и валидирует `pinLeft`/`pinRight`. `core/layout/create-columns.ts` сохраняет их как pin metadata; `view/table/table.tsx` явно запрещает pin. Снимать запрет до сквозной реализации нельзя.
2. Core нормализует визуальный порядок и согласует результаты двух отдельных модулей математики: обычных колонок и pin. Общая проекция получает рассчитанные ширины, группы, `s`, `V` и возвращает offsets, clip regions и набор видимых колонок. CSS Grid получает числовой результат через `--numbers-X`.
3. Core разделяет обычный направленный resize и независимое изменение pinWidth. Для pin вычисляется интервал из min/max и бюджета V-G за вычетом всех остальных pin; направленную компенсацию текущего fixed-resize на pin переносить не нужно. Ось указателя задаётся движущейся границей после O7. Ограничения крайних обычных колонок проверяются в контексте центра, а не глобальным индексом.
4. Runtime дополняет snapshot стороной pin, рассчитанным смещением/областью, контекстом resize и стороной ручки. `publish()` вместо текущего единственного `columnAxis.range(left, left + width, 1)` объединяет pinned и видимый центр. Runtime хранит независимые pinWidth, передаёт состояние чистому модулю pin и применяет его результат; формула бюджета не дублируется в runtime. Pin/order reconcile сохраняет состояние по columnId в ColumnRuntime (9.4.11); индексные anchors сбрасываются при перестройке схемы.
5. Browser дополняет текущий `pointerX()`: сейчас он всегда использует начало surface и при прокрутке закреплённой колонки создаст ложную дельту. Рабочая система координат определяется по активной колонке. Единственный scroll owner, измерения `numbers`, pointer capture на стабильном root и существующий Header portal сохраняются.
6. View применяет общую проекцию к существующим HeadCell/Cell без копий и отдельных таблиц. ResizeHandle получает сторону и физические направления из snapshot; формулы ширин, бюджетов и компенсации в него не переносятся. Стили задают только рассчитанное положение, clipping, фоны и локальное наложение.

#### 9.4.6. Разделение математических модулей — уточнение пользователя

Пользователь предложил выделить математику pin отдельно от текущей математики обычных колонок. Граница обоснована различием правил: обычный fixed-resize может компенсироваться auto и создавать overflow; pin меняет собственную ширину без изменения других pin и ограничивается общим бюджетом. Изменение правил бюджета или инициализации pin не должно требовать правок формул обычной компенсации.

Предлагаемое размещение — отдельный `core/pinning/` рядом с существующим `core/layout/`. Точное имя внутренних функций определяется при реализации; новых public entrypoints и пустых каталогов на этапе ТЗ не создаётся.

| Часть core                    | Вход                                                                                         | Результат и граница                                                                                                        |
| ----------------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Математика pin                | Описание pin, их собственные ширины и ограничения, V, резерв G, команда resize/инициализации | Ширины pin, PL/PR, предел активного pin, остаток бюджета, допустимость; без компенсации другими pin                        |
| Обычная математика            | Только обычные колонки, их base/manual/anchor, доступная ширина центра                       | Прежние правила auto/fixed и направленного resize; не знает pinLeft/pinRight, резерва G или pinWidth                       |
| Согласование и общая проекция | Результаты обеих математик, viewport и scroll                                                | Общие координаты, ширина поверхности, clipping и видимость для одного Header/Body; не изобретает собственные правила ширин |

Порядок вычисления при изменении pin:

```text
Команда и актуальное состояние из Runtime
  -> математика pin: независимая pinWidth, PL, PR, проверка бюджета
  -> доступная ширина центра = V - PL - PR
  -> обычная математика: реакция на доступную ширину центра
  -> общая проекция и геометрия
  -> единый snapshot Runtime
```

- Рост pin влияет на обычные колонки через доступную ширину центра. Он не записывает им новые manual и не вызывает их resize-команды от имени пользователя. Реакция центра на изменение доступной ширины остаётся ответственностью обычной математики.
- Обычный resize не меняет pinWidth и не использует pin как компенсирующие auto. Служебный согласующий расчёт не должен запускать обратный цикл, в котором overflow центра автоматически расширяет pin и снова уменьшает центр.
- Для вложенных Table различаются видимый бюджет и выделенная общая поверхность. В расчёт pin передаётся видимый бюджет данной Table; унаследованная широкая поверхность не разрешает расширять pin за пределы этого бюджета. Общая поверхность и минимальная потребность ребёнка согласуются существующим механизмом вложенности.
- Начальные ширины выбираются initializePins (initializePin — для одного кандидата) по источникам auto.base либо fixed.declaredWidth (9.4.8–9.4.9); она не считывается из результата обычной раскладки заново на каждом scroll или resize. Раздельное состояние по columnId хранит runtime, не чистые модули core.
- Модули могут использовать общие чистые примитивы вроде clamp и сумм, но не должны вызывать правила компенсации другого контекста. React, DOM, CSS и чтение токенов остаются вне обеих математик; на входе только логические числа numbers.
- Проверки разделяются на прежние регрессии обычной математики, независимые проверки pin и интеграционные последовательности согласования. Обязательные случаи: отсутствие изменения других pin, совместный предел обеих сторон, переходы pin/unpin и изменение ширины центра без потери обычных manual. Открытые случаи O7–O8 не считаются решёнными выбором границы модулей.

Шесть арифметических проверок прежнего предложения и две проверки компенсации внутри pin-группы не подтверждают новый контракт независимых ширин. Проверки нового бюджета реализованы в 9.4.7; инициализация и положение ручек остаются следующими этапами, проекция и единый scroll owner проверяются независимо.

Основание по внешнему поведению: официальная документация Google Sheets описывает [сохранение колонок на месте при прокрутке](https://support.google.com/docs/answer/9060449?co=GENIE.Platform%3DDesktop&hl=en) и [resize перетаскиванием границы](https://support.google.com/docs/answer/54813?co=GENIE.Platform%3DDesktop&hl=en). Она не раскрывает внутреннюю математику Google и не подтверждает предложенные здесь pinRight, компенсацию auto или политику нехватки места. Эти решения выведены из контрактов нашей таблицы и требуют указанных проверок.

#### 9.4.7. Реализованный первый срез core/pinning

Авторизация: «понял. приступай» после обсуждения первого математического среза
с явно заданными исходными ширинами в тестах. Scope: только бюджет, bounds и
независимый resize; инициализация pin, согласование обычной раскладки, runtime,
Header/Body и мышиные ручки этим поручением не подключаются.

- `PinColumn`: id, side, width, необязательные minWidth/maxWidth. Это внутренние
  данные чистой математики, не новые props React Column. Все размеры — логические
  числа numbers.
- `PinningViewport`: width и reserve. Резерв передаётся явно, 50 не зашито в модуль.
- `pinLayout` проверяет заданное состояние и рассчитывает leftWidth, rightWidth,
  totalWidth, centerWidth, budget и remaining.
- `pinResizeBounds` возвращает min/max выбранного id с учётом всех остальных pin
  обеих сторон. Отсутствующий собственный max или +Infinity не отменяет бюджет.
- `resizePin` ограничивает конечный запрос этим диапазоном, создаёт новый массив
  с изменённой активной шириной и возвращает новую геометрию. Другие pin не меняются,
  исходные объекты не мутируются. Отрицательный target ограничивается min;
  NaN/Infinity отклоняются.
- Некорректные размеры, min/max, дубли id, неизвестный id и уже превышенный бюджет
  отклоняются исключениями. Восстановление после сужения контейнера не выбирается
  скрыто: модуль работает с допустимым заданным состоянием, политика остаётся O8.
- Дробные размеры сохраняются без округления к токенам. Для суммы допускается
  только погрешность Number.EPSILON с учётом масштаба и количества слагаемых.
- Регрессии: 38 новых тестов, включая 4000 seeded resize-переходов, пример
  200/200/150 → 600/200/150 при V1000/G50, обе стороны бюджета, min/max,
  освобождение места после сужения, дробные границы, нулевые размеры и immutable inputs.
  Полный набор Table — 137 тестов в 7 файлах, TypeScript kit проходит.

Фасад модуля остаётся внутренним. Существующая математика обычных колонок и
публичный Table в этом срезе не менялись. Browser-проверка pin не заявляется:
пользовательская функция закрепления пока не подключена.

#### 9.4.8. Инициализация одного pin из обычной колонки

Авторизация: «приступай» после предложения брать auto.base без manual и исходную
объявленную fixed-ширину с последующим ограничением min/max и бюджетом. Scope:
чистый переход одной колонки; runtime, unpin, UI и одновременная инициализация
набора не подключаются.

- `PinWidthSource` — discriminated union: `{ mode: 'auto', base }` либо
  `{ mode: 'fixed', declaredWidth }`. Текущая растянутая width и manual не являются
  источниками нового pin. Модуль не импортирует обычную математику core/layout.
- `PinCandidate` содержит id, side, min/max и source. `initializePin` принимает
  существующие pin, viewport и одного кандидата, возвращает новый набор и PinLayout.
- Инициализация сначала проверяет возможность добавить min нового pin, затем
  применяет уже существующий resizePin к выбранной исходной ширине. Внешний caller
  получает один конечный результат; промежуточный min не публикуется в UI.
- Auto с base240 и width/manual5000 получает начальный кандидат240. Fixed с
  declaredWidth180 и текущей width6000 получает180. В обоих случаях затем действуют
  собственные min/max и бюджет за вычетом всех уже закреплённых колонок обеих сторон.
- Новый объект содержит только pin-данные. Обычный источник остаётся у caller,
  его base/manual/объявленная ширина не изменяются. Существующие pin сохраняют
  порядок, стороны, ширины и metadata; соседей инициализация не сжимает.
- Существующий id отклоняется, чтобы повторная инициализация не сбрасывала ранее
  изменённую pinWidth. Невалидный источник, min/max, сторона, существующее состояние
  или нехватка места даже для min отклоняются без частичного изменения.
- Нулевая начальная ширина допустима при min0, в том числе при занятом бюджете;
  искусственный положительный минимум не вводится. Дробные величины сохраняются
  с принятым допуском числовой арифметики.
- Операция одного перехода не задаёт политику начального распределения для целого
  набора pin. Не использовать её циклический вызов как неявно выбранный приоритет
  колонок при первоначальной загрузке схемы; согласованный расчёт набора добавлен в 9.4.9.
- Проверки: 29 новых тестов, включая 1000 seeded single-pin переходов; полный
  набор Table — 166 тестов в 8 файлах. TypeScript kit проходит. Browser acceptance
  pin не заявляется: новый helper ещё не используется runtime/View.

#### 9.4.9. Атомарная инициализация набора pin

Авторизация: «согласен. продолжай» после предложения общего расчёта желаемых ширин,
пропорционального уменьшения части сверх min и отказа при нехватке места для min.
Scope: чистая математика в core/pinning, без runtime/View.

- `initializePins` получает существующие pin и набор новых PinCandidate. Существующие
  pin сохраняют ширины, стороны, metadata и объекты; их размер вычитается из общего
  бюджета до распределения. Источники новых ширин прежние: auto.base/fixed.declaredWidth.
- Желаемая ширина каждого нового pin сначала ограничивается его собственными min/max.
  Если набор помещается, эти значения сохраняются; свободное место не заполняется
  принудительно. Если не помещается сумма min, весь переход отклоняется атомарно.
- Иначе распределяется только часть сверх min, с одним коэффициентом для всех новых
  кандидатов обеих сторон. Сторона pin, его место в декларации или обходе не дают
  приоритета. Результирующие ширины остаются между min и ограниченным желанием.

```text
B = V - G - сумма ширин существующих pin
m[i] = minWidth[i] либо0
p[i] = clamp(sourceWidth[i], m[i], maxWidth[i])
M = sum(m[i])
E = sum(p[i] - m[i])

если M > B: конфликт
если E <= B - M: width[i] = p[i]
иначе: alpha = (B - M) / E
       width[i] = m[i] + alpha * (p[i] - m[i])
```

При E=0 деление не требуется, результат — min. Если M=B, коэффициент0.
Числовые сравнения используют принятый допуск арифметики. Большие конечные
избытки нормализуются при расчёте коэффициента, чтобы их сумма не превращала
весь результат в0 из-за переполнения; при underflow коэффициента используется
эквивалентное распределение доли бюджета.

- Пример: два новых pin хотят600 с min100, общий бюджет950 →475/475.
  При существующем pin300 и двух новых желаниях500/500 с min100/200 остаётся650:
  новые получают300/350, старый сохраняет300. Это сжатие относительно min,
  а не пропорциональное уменьшение всей ширины.
- `initializePin` использует ту же реализацию для одного кандидата. Выход сохраняет
  порядок existing и кандидатов, расчёт сумм канонизирован по id. Перестановка
  входа не меняет назначенные ширины по id. Дубли и невалидные кандидаты отклоняют
  весь переход без частичного изменения.
- Пропорциональный расчёт выполняется только при совместной инициализации новых pin.
  Последующий resize остаётся независимым; рост одного pin не перераспределяет другие.
- Проверки: 19 новых тестов с 300 seeded наборами, все перестановки трёх кандидатов,
  min/max, пустые/нулевые/locked наборы, атомарный отказ и крайние числовые диапазоны.
  Прежние 29 тестов одного перехода сохранены. Полный набор Table —185 тестов в9 файлах;
  TypeScript kit проходит. Runtime, unpin и пользовательская функция pin ещё не подключены.

#### 9.4.10. Согласование геометрии pin и обычных колонок

Авторизация: «согласен. продолжай» после предложения общего расчёта ширин,
позиций и границ трёх областей. Scope: чистый core, без подключения runtime/View.

`core/geometry/table-layout.ts` содержит два независимых от среды вычисления:

- `tableLayout` принимает обычное состояние всей видимой упорядоченной схемы,
  готовые pinWidth по id, `{ width, reserve, surfaceWidth? }` и необязательный
  LayoutAnchor центра. Дубли id и pin вне схемы отклоняются. Суммы pin вычисляются
  в порядке схемы; порядок хранения состояния не влияет даже на дробные суммы.
- Pin проверяются существующим `pinLayout` и исключаются из обычного набора.
  Их прежняя обычная width/manual не участвует. Расчёт не инициализирует pin
  заново и не запускает resize другой области. Исходное состояние не мутируется.

```text
V = width, S = surfaceWidth либо V; S >= V
C = max(0, V - PL - PR)
CS = max(0, S - PL - PR)

без surfaceWidth: center = automatic(centerColumns, C, centerAnchor)
с surfaceWidth:   center = sharedLayout(centerColumns, CS, C, centerAnchor)

T = PL + center.total + PR
overflow = max(0, T - V)
```

Для вложенной таблицы бюджет pin ограничен V, а не S. Выделенная широкая
поверхность заполняется обычной математикой центра. `center.layout.overflow`
по прежнему контракту относится к CS; общий overflow — к V. Обычный LayoutAnchor
содержит базы только центра в его текущем порядке; runtime reconciliation по id
ещё не реализован. Его индексы нельзя брать из полного порядка L/C/R.

- Результат содержит порядок L/C/R с сохранением порядка схемы внутри каждой
  группы, sourceIndex, ширины, offsets в содержимом и внутри группы, layout центра,
  суммы pin и смежные clip-границы `[0,PL]`, `[PL,V-PR]`, `[V-PR,V]`.
  Погрешность накопления на границе бюджета не создаёт отрицательный центр
  или перекрывающиеся области; ширины pin при этом не округляются.
- `projectColumns(layout, scroll)` возвращает displayOffset и shift по 9.4.2.
  Ширины не пересчитываются. Правые pin проецируются от V-PR и собственного
  regionOffset; вычитание их ширин из огромного T не используется. Центр
  получает offset-scroll, pin остаются у краёв. Scroll должен быть конечным;
  он не ограничивается локальным overflow, поскольку owner может быть общим.
  Непредставимые конечными числами результаты отклоняются.
- Все координаты — логические numbers. Одна проекция предназначена для Header
  и Body; runtime/View ещё не применяют её. Новый scroller, portal, public prop,
  CSS px или дополнительный слой состояния не вводятся.
- Без pin сохраняется прежний automatic/sharedLayout, включая directed anchor,
  min/manual и отказ при невозможном заполнении. Центр без auto по-прежнему
  отклоняется: O8 не закрыт созданием фиктивной auto. Недопустимый pin-бюджет
  также отклоняется; внешнее сужение viewport не запускает скрытое сжатие/unpin.
- Возвращаемый overflow — описание геометрии. Разрешать ли появление скролла
  центра вследствие роста pin, остаётся O7; этот расчёт не выбирает такую политику.
- Проверки: 38 новых тестов, включая 2000 seeded независимых resize pin с
  согласованием центра и scroll-проекцией. Без pin проверена совместимость с
  automatic/sharedLayout; сохранены directed anchor и manual, покрыты общий
  бюджет, дробные/нулевые размеры, широкая вложенная поверхность и атомарный отказ.
  Полный набор Table —223 теста в10 файлах; TypeScript kit проходит. Browser/UI
  acceptance этим математическим этапом не заявляется.

#### 9.4.11. Первый runtime закрепления

Авторизация: «согласен. продолжай» после предложения подключить готовую математику
к TableRuntime, отдельное хранение pinWidth, инициализацию, resize и единый snapshot.
Первый срез ограничен декларативным закреплением; React/browser ещё не подключены.

- `runtime/columns/ColumnRuntime` владеет обычными настройками, отдельными pinWidth,
  anchors, nested demand, общей геометрией и операцией resize. TableRuntime
  сохраняет строки, их измерения, раскрытие и публикацию совместного snapshot.
- `createGeometryColumns` сохраняет pinLeft/pinRight как pin metadata. Резерв
  первоначально задавался явно внутренней опцией pinning.reserve; актуальный
  default50 и публичное переопределение описаны в 9.4.17. Обязательна auto в центре; недопустимая схема получает
  ошибку, фиктивная auto не создаётся.
- До измерения ненулевого viewport инициализация pin отложена, включая reserve0.
  Затем используется initializePins из auto.base/fixed declaration. Растянутая
  обычная width/manual не становится pinWidth. Данные, scroll и нейтральный
  configure не инициализируют pin заново.
- Основное адаптивное поведение при нехватке места согласовано пользователем:
  когда сохранённый набор не помещается в видимый бюджет, закрепление всего набора
  приостанавливается. Это штатная политика компонента, а не временное решение. Обычная таблица получает
  всю схему и свои настройки, pinWidth остаются сохранены. При возвращении места
  восстанавливается прежнее закрепление с прежними размерами. Если ещё не помещаются
  min первоначального набора, частичной инициализации нет. Это поведение runtime;
  чистый pinLayout по-прежнему отклоняет невместимый вход.
- PinBudgetError отличает нехватку бюджета от ошибок данных. Runtime не выбирает
  recovery по тексту исключения. Ошибки размеров и невозможного заполнения центра
  не маскируются fallback; невыполнимый запрос во время pin drag сохраняет последнюю
  допустимую геометрию.
- Обычный beginResize работает только в контексте центра. Pin операция запускается
  отдельным beginPinResize(id,x,edge), где caller явно задаёт движущуюся границу.
  Для edge=left ширина растёт при уменьшении x, для right — при увеличении.
  X — координата viewport в numbers; scroll центра не меняет её. Спорная сторона
  визуальной ручки не назначается этим внутренним API.
- Собственные min/max и общий бюджет обеих сторон ограничивают resize одного pin.
  Его обычные настройки и другие pin не меняются. Крайний pin не теряет разрешение
  из-за глобального последнего индекса. У центра сохраняется собственное правило
  последней колонки. Pin bounds публикуются как числовой интервал; физические
  left/right индикаторы для pin ещё должен связать view с выбранной стороной ручки.
- Рабочая опора и rollback отдельны. Выход за min/max и разворот не меняют опору;
  внешнее изменение геометрии выполняет rebase только рабочей опоры. При смене
  контекста active/suspended незавершённая операция отменяется с rollback.
- Состояние сопоставляется по id. Reconfigure сохраняет неизменённые обычные
  запросы и pinWidth, удаляет исчезнувшие id и сбрасывает индексные anchors при
  перестройке схемы. Изменённая декларация размера переинициализирует только её pin.
  Декларативное снятие флага не переносит pinWidth в обычное состояние; отдельные
  пользовательские controls pin/unpin в этом срезе не создаются.
- Snapshot содержит визуальный порядок L/C/R, sourceIndex, region, offsets/shift,
  границы областей и active/suspended с сохранёнными pinWidth. Виртуальный набор
  объединяет pin с окном центра без дубликатов; строки и измерения остаются общими.
  Изменение ширин инвалидирует версии измерений, scroll меняет только проекцию.
- Видимый бюджет не растёт от широкой поверхности вложенного Table или nested
  demand. Они передаются в общую геометрию как выделенная поверхность. Новые scroll
  owner, portals и независимые row state не добавляются.
- Дополнительная политика переполнения центра не выбирается этим runtime; O7
  остаётся открытым в этой части. React guard на pin сохраняется до завершения
  view/browser, clipping, focus/ARIA и проверки реального приложения.

Проверки: 31 новый тест через публичные методы TableRuntime, включая 800 seeded
resize/scroll/fallback/restore, удержание за min/max и развороты, cancel/rebase,
инициализацию и сохранение по id, виртуализацию, nested surface и stale measurements.
Прежние 223 теста сохранены, полный набор —254 в11 файлах. TypeScript kit проходит.
Browser acceptance pin ещё не выполняется: интерфейс не подключён.

#### 9.4.12. Отображение pin и проверка в приложении

Авторизация: просьба проверить выбранные pin на Складе. Public Table принимает

#### 9.4.13. Синхронизация горизонтального scroll портального Header

Центральные HeadCell не получают -scroll через React: это давало задержку относительно
нативно прокручиваемого тела. Browser HeaderScroll использует ScrollTimeline от того
же реального scroll owner. Native progress соответствует scrollLeft / максимальный
scroll; from/to transform задают тот же диапазон, переведённый в numbers, с учётом
постоянного локального смещения таблицы. Keyframes используют --numbers-1.

На scroll меняется native progress, а анимации сохраняются. Новые виртуальные ячейки
подключаются к той же timeline, исчезнувшие освобождаются. Диапазон обновляется при
геометрическом изменении. При отсутствии API применяется непосредственная запись
transform браузерным адаптером без ожидания React. Переход в flow очищает эффекты.
Pin и существующий вертикальный portal lifecycle не меняются.

Основание API: [CSSWG Scroll-driven Animations](https://drafts.csswg.org/scroll-animations-1/#scrolltimeline-interface).
Спецификация допускает асинхронную выборку scroll-driven эффектов без выполнения
script на каждом сдвиге. Фактическая работа native пути проверяется в приложении;
это не обещание одинакового compositor поведения всех браузеров.

#### 9.4.14. Владение критичной DOM-геометрией

Browser-адаптер применяет готовые размеры Body/Row, ширины поверхности и grid tracks,
размещение pin и вертикальное положение/flow-portal переход Header непосредственно
при runtime publish. React владеет содержимым и составом виртуального окна; одни и
те же геометрические свойства не должны одновременно записываться React и адаптером.
Новые DOM-узлы согласуются в layout effect до paint. Все длины Table сериализуются
через --numbers-X; core остаётся независимым от DOM и CSS.

Компенсация вертикальной прокрутки выполняется после применения нового scroll
extent. Проверка у нижней границы: рост строки над опорой на200 увеличивает Body
с800 до1000, native scrollTop — с428 до628 при header28 и viewport400. Применение
scrollBy до изменения DOM высоты обрежет компенсацию и считается дефектом.

Измерения регистрируются по DOM identity. При смене версии геометрии адаптер
повторно считывает смонтированные элементы без ожидания повторной регистрации
через React или дополнительного события ResizeObserver; stale queued measurements
по-прежнему отклоняются runtime. Вложенная Table имеет своего DOM-владельца.

Системный Scrollbar привязывает движение thumb к source viewport через native
ScrollTimeline, с прямым DOM fallback. React не хранит координату или размер thumb;
он управляет наличием и видимостью track. Drag использует свежую геометрию ref.
Вертикальный Header сохраняет существующий программный механизм: его DOM-стили
обновляются по scroll напрямую, но этот путь не объявляется compositor-native.

#### 9.4.15. Подключение мышиных ручек pin

По поручению пользователя подключён отдельный pin resize к существующему control.
У левого pin движущаяся граница справа, у правого слева. Середина ручки numbers10
и середина разделителя numbers3 совпадают с этой геометрической границей.
Полоса рисуется симметрично, только у внутреннего края каждой pin-группы.
Контент обрезается отдельно, чтобы внешняя половина ручки оставалась доступна.

Runtime публикует resizeEdge, resizeBounds и физические left/right разрешения.
Browser вызывает beginPinResize; его координата указателя относится к viewport,
поэтому scroll центра не добавляется к pin delta. Обычный beginResize сохраняет
координату содержимого. Keyboard вызывает тот же выбор операции. Резерв и min/max
ограничивают независимый размер pin; другие pin не компенсируют изменение.
Смена масштаба/viewport выполняет rebase рабочей опоры; cancel восстанавливает
исходный checkpoint. Последняя колонка центра сохраняет прежний запрет resize;
последний правый pin может иметь ручку слева при явном resizable=true.

#### 9.4.16. Основная политика при нехватке места для pin

По уточнению пользователя приостановка закрепления является штатным адаптивным
поведением Table, а не временным обходом ограничения реализации.

- Условие: сохранённые ширины обеих pin-групп вместе с резервом центра не помещаются
  в видимую ширину: PL+PR+G > V. Порог определяется сохранёнными ширинами, не только min.
- Вся группа pin переходит в обычную прокручиваемую раскладку. Частичный выбор,
  автоматическое уменьшение соседних pin и приоритет одной стороны не вводятся.
- Настройки pin и pinWidth сохраняются отдельно от обычных настроек колонок.
  Это не пользовательское снятие pin и не потеря сохранённого выбора.
- Когда сохранённый набор снова удовлетворяет PL+PR+G <= V, закрепление обеих
  групп восстанавливается с сохранёнными размерами.
- До первой успешной инициализации pin весь набор остаётся в обычном режиме,
  если даже его min не помещаются. При смене контекста активный drag отменяется
  по существующему правилу rollback. Ошибки схемы не маскируются нехваткой места.

Слово «временное» относится к состоянию закрепления при узком viewport, но не
к статусу этой политики. Дополнительные ограничения overflow центра из O7
этим решением не определяются.

#### 9.4.17. Резерв центра по умолчанию

По решению пользователя `ColumnRuntime` применяет reserve=50 логических единиц
numbers. Consumer может переопределить его через `layout.pinning.reserve`, включая
`0`. Отсутствующий `pinning`, пустой объект и `reserve: undefined` используют 50.
NaN, Infinity и отрицательные значения остаются ошибкой. Чистая математика core
получает уже разрешённый числовой reserve и собственного default не назначает.

Отсутствие override и явное значение 50 эквивалентны: такая смена конфигурации
не отменяет активный resize и не переинициализирует ширины. Резерв участвует
в общем бюджете pin и пороге адаптивной приостановки/восстановления (9.4.16).
Склад использует default без явного pinning.reserve. Политика O7 не изменяется.

#### 9.4.18. Numbers tokens в декларациях колонок

По уточнению пользователя width/minWidth/maxWidth в проверочном consumer Склад
задаются явно как `var(--numbers-X)`. Возможность передать число сохраняется;
число означает логические единицы numbers, не голые CSS px. Конфигуратор переводит
существующий token шкалы numbers в логический размер до передачи в core. Целые
имена 0–3000 и дробные имена темы поддерживаются; ошибочный numbers token
отклоняется. Width с token — fixed, отсутствие width сохраняет auto. Проверка
min/max и обязательной auto выполняется после нормализации. Browser продолжает
учитывать масштаб numbers-1 и сериализовать рассчитанную геометрию через tokens.
Все три уровня Склада используют этот формат. Семантика pin/resize не меняется.

### 9.5. Постоянный компенсатор и общая правая граница resize — 2026-11-13

Это уточнение заменяет прежние требования обязательной пользовательской auto,
запрета resize последней колонки и ошибки при исчерпании суммарного maxWidth.
Исторические этапы 9.4 описывают предыдущие ограничения реализации.

- Runtime всегда содержит служебную auto-колонку после пользовательских колонок центра,
  перед правой pin-группой. Пользователь не объявляет и не настраивает её.
- Пользовательские auto получают место первыми. Компенсатор занимает остаток:
  `F = max(0, C - sum(widths of other columns))` в соответствующем контексте раскладки.
  При переполнении F=0; общая поверхность и nested demand остаются согласованными.
- При F=0 служебный track и DOM-ячейки не отображаются. При F>0 сохраняются фон
  и разделители строк, но отсутствуют контент, измерение ширины, sort и resize.
- Любая пользовательская колонка, включая последнюю, поддерживает resizable=true.
  Уменьшение auto до min/floor допустимо: освободившееся место занимает компенсатор.
  Ручные bases сохраняются при нейтральных обновлениях; reset возвращает автоматическую раскладку.
- Для всех ручек browser ограничивает перемещение вправо видимой правой границей
  таблицы, с учётом точки захвата, numbers scale и scroll owner. Быстрый перескок
  одним pointermove обрабатывается тем же ограничением. Разворот не меняет точку отсчёта.
- Keyboard использует ту же границу. Перед завершением изменённого resize проверяется
  итоговое положение края; onResize вызывается один раз с итоговой шириной после коррекции.
- Это не запрет overflow таблицы: ранняя колонка может сдвинуть последующие за viewport.
  Ручки и pin-разделители сами не должны увеличивать scrollable width. Header использует
  overflow:clip по внешней границе, сохраняя выступы controls над соседними колонками.
- Доступность индикаторов у правого края обновляется DOM-адаптером без зависимости
  синхронизации scroll от React. У pin сохраняются зеркальная сторона и общий бюджет.

### 9.6. Пустое состояние — 2026-11-14

При отсутствии записей Table отображает только Empty внутри своего контейнера. Самостоятельная таблица сохраняет внешний border; встроенная сохраняет обычный embedded-визуал без внешнего border. Header, Body, ячейки, resize controls и табличные ARIA-роли не монтируются.

Ширины колонок не определяют ширину пустого блока и не создают горизонтальную прокрутку. Empty вложенной таблицы ограничен доступным viewport общей поверхности и остаётся видимым при горизонтальной прокрутке родителя. Пустая вложенная таблица не предъявляет родителю минимальную ширину своих колонок.

Runtime сохраняет декларации, измерения хедера и ручные ширины колонок. При возвращении записей Header/Body восстанавливаются с этими настройками и обычной геометрией. Переключение пустого состояния само не вызывает onResize. Фактическая высота Empty по-прежнему измеряется browser observer; пустому состоянию не добавляется высота отсутствующего хедера.

| A65 | Один pin на стороне, resizable=true; проверяются края обычной области                           | Глобальный индекс не запрещает resize pin автоматически; ограничения центра отдельны; сторона ручки соответствует согласованной опорной геометрии O7                                      |
| A66 | Закреплённые области перестают помещаться из-за resize или сужения viewport                     | Применяется согласованная O8; нет перекрытия областей, недоступного центра, потери manual и отдельного scrollbar                                                                          |
| A67 | Три уровня Expand с разными pin и одним horizontal scroll owner                                 | Каждый ограничивает pin своим видимым контейнером; нет наследования схемы, глобального z-index или собственной прокрутки ребёнка                                                          |
| A68 | Numbers-scale, transform, дробные ширины, клавиатурный resize и controls у края центра          | Геометрия/дельты нормализованы; ArrowLeft/Right соответствуют физическому движению; focus доводится до видимой части центра                                                               |

A14–A16 и переход из направленного resize к resize контейнера проверяются отдельно от формул глобальной автоматической раскладки. Предыдущая численная модель глобального распределения не подтверждает эти новые сценарии.

Сценарии O1–O8 должны получить ожидаемые результаты до реализации соответствующих переходов. Их нельзя считать принятыми по одному факту существования формул в этом документе.

## 11. Требования к проверке реализации

1. Проверить арифметические инварианты: ограничения размеров, суммы, координаты и величину переполнения.
2. Проверить последовательности событий: окно уменьшили и вернули; auto расширили и вернули к base; fixed изменили справа, завершили drag, затем изменили контейнер.
3. Проверить порядок колонок: auto только справа, только слева, с обеих сторон и отсутствие auto справа от последней колонки.
4. Проверить взаимодействия в браузере с реальными React-ячейками, включая выделение, controls, закрепление и изменяемую высоту.
5. Проверять производительность в production-сборке на согласованной нагрузке. Измерять время кадров, задержку resize, объём DOM и память; размер массива данных сам по себе не является показателем скорости.
6. Проверить, что стоимость отображения ограничена viewport и overscan, а не полным числом ячеек.
7. Выбрать worker или дополнительные механизмы ускорения только после установления нагрузки и стоимости расчётов. Проверка геометрии не является доказательством ускорения.
8. Проверить программное закрепление при внешнем scroll owner, динамических topOffset/headerHeight, горизонтальном скролле, виртуализации, закреплённых колонках и активном resize.
9. Проверить адаптивные темы numbers, преобразование измерений, валидность токенов и сохранение общей ширины при дробных результатах.
10. Отдельно проверять core на обычных данных, runtime на последовательностях событий и view на реальном браузерном поведении. Логика расчёта не должна дублироваться в слоях.
11. Проверить строки динамической высоты: уточнение оценок выше и ниже viewport, изменение самой опорной строки, horizontal unmount высокой ячейки, изменение ширины и содержимого, асинхронные размеры, удаление опоры и совместную работу с нативным scroll anchoring.
12. Для pin отдельно проверить общую раскладку и проекцию, зеркальную операцию после выбора O7, бюджет O8, смену порядка без потери manual, ARIA/focus и вложенные таблицы с единым scroller. Арифметическая проверка предложения не заменяет browser acceptance готовой реализации.

Числовые бюджеты производительности и целевые устройства согласовываются на этапе прототипа. ТЗ не утверждает неподтверждённую гарантию FPS.

## 12. Решения, необходимые для завершения контракта

### O1. Граница заполнения — решение принято

Сумма ширин не меньше ширины контейнера благодаря постоянному компенсатору. Последняя пользовательская колонка поддерживает resize; общее ограничение правой границы и актуальная политика описаны в 9.5.

### O2. Срок жизни reference и floor

Необходимо определить поведение при смене данных, загрузке новых строк, изменении содержимого, шрифтов, видимости и набора колонок, повторном открытии таблицы и явном сбросе размеров.

Первоначальная ширина контейнера не ограничивает измеренный контентный floor. Runtime сохраняет максимум увиденного содержимого при виртуальном unmount и сбрасывает накопления при смене набора данных или схемы; явный minWidth остаётся нижней границей. Дополнительные правила срока жизни опорной раскладки и ручных размеров требуют отдельного согласования.

### O3. Верхние пределы и обязательное заполнение

Если `F + sum(maxAuto) < W`, заполнить контейнер без нарушения max невозможно. Для произвольно растущего контейнера гарантировать заполнение можно при наличии хотя бы одной auto без жёсткого верхнего предела. Альтернативное поведение для незаполненного остатка требует отдельного решения.

### O4. Определение контентной потребности

Необходимо выбрать правила переноса, ограничения содержимого и область измерений: все строки, доступные измеренные строки или оценка. Отдельно определить обновление измерений при виртуализации, изображениях, асинхронном содержимом и смене шрифтов.

Нельзя обещать точный максимум по всем строкам, если измерены только видимые ячейки.

### O5. Доли нескольких auto

Нужно закрепить способ первоначального распределения и компенсации справа: равные ширины свободных колонок, пропорции или другой алгоритм. Ограничения каждой колонки должны соблюдаться при любом выбранном способе.

### O6. Resize контейнера после направленного resize

Исторический пример resize последней колонки больше недоступен в UI. Вопрос сохраняется для внутренних fixed: например, `[auto 400][fixed 200][auto 400]` с floor auto 100 после увеличения средней fixed до 700 даёт `[auto 400][fixed 700][auto 100]`, T=1200.

Нужно определить результаты последующих W=900, W=1001 и W=1200, включая обратное возвращение к W=1000. Наивный глобальный расчёт способен изменить auto слева уже при прежнем W и отменить направленный результат.

Согласованное решение должно различать автоматическую базу, результат направленной операции и пользовательские запросы; не создавать произвольного нового контентного минимума для auto слева; не вызывать скачок только из-за смены обработчика события.

### O7. Контексты и независимое изменение pin — частично согласовано

Последнее уточнение пользователя: pin меняют ширину независимо, без компенсации другими pin, в пределах общего бюджета обеих сторон. Постоянная суммарная ширина pin-группы не требуется. Pin исключены из общего контекста resize обычных колонок; крайние границы центра определяются у pin.

Стороны ручек определены в 9.4.15 при подключении UI: у левого pin справа, у правого слева. Ранее обсуждавшееся обратное расположение не соответствует движущимся границам при независимом росте и закреплённых внешних краях. Ручка следует за указателем; прежняя формула направленной компенсации fixed на pin не переносится.

Рост pin сокращает место центра. Нужно отдельно определить пересчёт обычных колонок и допустимость его overflow при fixed/min/manual; независимость ширин других pin это не решает. Если требование «не создают скролл» означает запрет появления любого нового horizontal overflow, одного ограничения суммы pin недостаточно.

### O8. Начальная ширина pin и резерв центра

Общий контракт принят: PL+PR <= V-G, где V — видимая ширина Table; обе стороны учитывают друг друга. --numbers-50 приведён пользователем как пример резерва G. Конкретное значение и новый публичный prop этим пока не назначаются.

Для одного перехода источник выбран и реализован в 9.4.8: auto.base без manual либо исходная fixed.declaredWidth, затем min/max и свободный общий бюджет. Набор одновременно закрепляемых колонок инициализируется по 9.4.9 с общим коэффициентом сжатия части сверх min.

Нужно определить:

- Обычные настройки и pinWidth хранятся отдельно в ColumnRuntime по id (9.4.11). Декларативное изменение флага не переносит pinWidth поверх обычной настройки. Пользовательские controls pin/unpin ещё не реализованы.
- Основная политика при внешнем сужении V: закрепление всей группы отключается на время нехватки бюджета; pinWidth и настройки сохраняются, при возвращении достаточного места закрепление восстанавливается (9.4.16). Это утверждённое поведение компонента. Автоматического сжатия соседей и приоритетов сторон нет.
- Первый runtime требует auto в центре. Схемы без обычных колонок или с одними fixed в центре отклоняются; расширение этого режима в текущий scope не входит.

Адаптивная приостановка pin описана в 9.4.11 и утверждена пользователем как основная политика в 9.4.16. Резерв по умолчанию — 50 логических numbers; layout.pinning.reserve переопределяет его, включая 0 (9.4.17). Стороны UI-ручек определены в 9.4.15; дополнительная политика переполнения центра остаётся в O7.

## 13. Результат будущей реализации

Результатом должен стать совместимый React-компонент Table с архитектурой core/runtime/view, собственной геометрией, размещением колонок через рассчитанные токены CSS Grid, направленным resize, программным закреплением хедера и колонок, предсказуемым горизонтальным переполнением и виртуализацией динамических строк с измерениями и корректировкой скролла. Сторона resize при pinRight и допустимость закреплённых областей определяются решениями O7–O8. Формулы и переходы состояния должны быть покрыты сценариями приёмки, а взаимодействия — проверены в браузере.

Текущий документ является основанием для завершения контракта и подготовки прототипа. Открытые решения O1–O8 не дают разрешения выбрать произвольное поведение или начать миграцию потребителей без отдельного запроса на реализацию.
