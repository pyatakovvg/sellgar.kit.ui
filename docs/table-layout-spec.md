# Техническое задание на архитектуру и геометрию компонента Table

- Статус: проект ТЗ. Требования из обсуждения сведены в единый контракт; нерешённые случаи перечислены в разделе 12.
- Дата: 2026-11-06.
- Обновлено: 2026-11-07.
- Пакет: `@sellgar/kit`.
- Целевой репозиторий: `frontend/sellgar.ui.admin/library/sellgar.kit.ui`.
- Область: архитектура core/runtime/view, расчёт колонок, токены размеров, ручной resize, программное закрепление хедера и виртуализация.

Таблица должна автоматически заполнять доступную ширину и поддерживать предсказуемое изменение колонок мышью. Ручка resize находится справа от колонки; при перетаскивании её правая граница следует за указателем, а левая остаётся на месте. Ограничения содержимого и выбранные пользователем размеры определяют момент появления горизонтального переполнения.

ТЗ сохраняет публичный API и React-представление. Внутренняя архитектура разделяется на core, runtime и view. Колонки размещаются через CSS Grid по рассчитанному шаблону с токенами `--numbers-X`; закреплением хедера управляет runtime на основе расчётов core. Выбор D3, другой библиотеки, worker или GPU не является требованием.

## 1. Объём работ

### 1.1. Входит в будущую реализацию

1. Собственная координатная модель строк и колонок.
2. Начальная автоматическая раскладка с фиксированными и auto-колонками.
3. Реакция на изменение ширины контейнера.
4. Ручное расширение и сужение колонок с правой стороны.
5. Контентные ограничения, `minWidth`, `maxWidth` и горизонтальное переполнение.
6. Сохранение корректной геометрии после завершения resize.
7. Виртуализация строк и колонок при сохранении React-содержимого ячеек, с динамическими высотами строк, измерениями и корректировкой позиции скролла.
8. Проверка совместимости существующих сценариев Table: заголовков, закрепления, selection, sort, tree, expansion, empty state и взаимодействий со строками.
9. Разделение правил, состояния работающей таблицы и React-представления между core/runtime/view.
10. Программное закрепление хедера относительно выбранного scroll-контейнера с учётом границ таблицы и горизонтального скролла.

### 1.2. Ограничения реализации

- Существующая внутренняя архитектура Table не является обязательной основой.
- Не использовать HTML table или CSS table layout как механизм геометрии таблицы.
- Использовать CSS Grid для размещения колонок по автоматически сформированному `grid-template-columns`. Размеры колонок определяет модель; CSS Grid получает результат расчёта, а не становится владельцем правил auto/fixed, resize и компенсации.
- Размеры в CSS-шаблоне передавать через токены `--numbers-X`. Прямая сериализация расчётной ширины как `${width}px` не соответствует контракту кита.
- Для закрепления хедера использовать программное управление. `position: sticky` не является механизмом его закрепления; CSS применяется для отображения рассчитанного положения.
- CSS продолжает использоваться для оформления, позиционирования рассчитанных элементов и внутреннего устройства React-содержимого ячеек.
- React остаётся renderer содержимого. Переписывание произвольного JSX в графические команды Canvas/WebGL не входит в задачу.
- Существующие публичные imports, compound API, render scopes и callbacks должны сохранять совместимость. По уточнению пользователя Column принимает `resizable?: boolean`: resize выключен по умолчанию и включается только через `resizable={true}` для конкретной колонки.
- Конфигурация без видимой auto-колонки является ошибочной. Нельзя молча преобразовывать произвольно выбранную fixed-колонку в auto.
- Worker и GPU допустимы только при обоснованной необходимости. Они не должны менять результаты геометрии и контракт взаимодействий.

Подготовка этого ТЗ не включает реализацию компонента, установку зависимостей, commit или push.

### 1.3. Границы core/runtime/view

| Слой    | Ответственность                                                                                                                                                                              |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Core    | Модель строк и колонок, правила auto/fixed, ограничения, расчёт геометрии и направленного resize, видимая область, расчёт ограниченного положения хедера                                     |
| Runtime | Состояние экземпляра таблицы, опорная раскладка, ручные запросы, активный drag, scroll owner и viewport, получение измерений, нормализация единиц, вызов core, публикация snapshots и команд |
| View    | Публичное React-представление, заголовки, строки, ячейки и controls, сериализация рассчитанных размеров в токены, CSS Grid и применение рассчитанного положения хедера                       |

Core получает обычные данные и состояние, возвращает результат вычисления. Он не зависит от React, DOM, observers, CSS Grid или способа отображения хедера. Браузерные измерения и подписки принадлежат runtime либо его платформенным адаптерам.

Runtime является владельцем текущего состояния работающей таблицы. View подписывается на его snapshots и передаёт команды; самостоятельный расчёт компенсации, опорных размеров или правил закрепления в React-компонентах недопустим.

```text
View: пользовательское действие
  -> Runtime: команда и актуальное состояние
  -> Core: расчёт следующего состояния и геометрии
  -> Runtime: публикация snapshot
  -> View: отображение рассчитанного результата
```

Названия слоёв не требуют создания отдельных публикуемых пакетов. Конкретное размещение файлов определяется при проектировании реализации с сохранением этих границ.

## 2. Термины и величины

Расчёты размеров и смещений выполняются в согласованных логических единицах шкалы `numbers`. Доступная ширина исключает внешние отступы и занятое вертикальным scrollbar пространство. Размер ячейки включает её внутренние отступы и границы по единой принятой box-модели.

Измерения DOM и координаты указателя поступают в браузерных CSS px. Runtime приводит их к логическим единицам перед расчётом. Число в имени `--numbers-600` нельзя безусловно считать равным 600 CSS px: адаптивная тема может задавать значение токена в `vw`.

При линейном масштабе шкалы:

```text
scale = фактическая длина одной единицы numbers в CSS px
logicalLength = measuredCssLength / scale
logicalPointerDelta = measuredCssPointerDelta / scale
```

Определять масштаб нужно по разрешённой браузером длине токена, а не через чтение числовой части строки с неизвестной единицей. Изменение масштаба темы требует обновить преобразование измерений и текущего drag без переписывания сохранённых логических запросов.

View автоматически строит шаблон из результата модели, например:

```css
grid-template-columns:
  var(--numbers-200)
  var(--numbers-600)
  var(--numbers-200);
```

Числовой трек в таком шаблоне не меняет семантический режим колонки: рассчитанная auto остаётся auto в модели. Сериализатор должен ссылаться на реально объявленные токены и учитывать формат дробных имён, например `--numbers-0_5`. Нельзя создавать ссылки на несуществующие токены или независимо округлять все колонки с потерей общей суммы ширин.

Числа в формулах и примерах далее обозначают логические единицы шкалы `numbers`.

| Обозначение        | Значение                                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| `W`                | Текущая доступная ширина контейнера                                                                 |
| `f[i]`             | Фактическая ширина fixed-колонки                                                                    |
| `F`                | Сумма `f[i]` всех активных fixed-колонок                                                            |
| `content[i]`       | Измеренная потребность содержимого колонки по выбранным правилам переноса и ограничения содержимого |
| `reference[i]`     | Ширина auto-колонки в опорной автоматической раскладке                                              |
| `floor[i]`         | Сохранённый нижний предел автоматического сжатия                                                    |
| `base[i]`          | Ширина auto-колонки без её ручного расширения в текущем состоянии раскладки                         |
| `manual[i]`        | Сохранённый запрос ручного расширения auto; может отсутствовать                                     |
| `width[i]`         | Фактическая ширина колонки                                                                          |
| `min[i]`, `max[i]` | Явные ограничения ширины; отсутствие максимума означает `+∞`                                        |
| `T`                | Суммарная ширина колонок                                                                            |
| `overflow`         | Величина горизонтального переполнения таблицы                                                       |

`reference`, `floor`, `base` и `manual` — разные величины. Изменение фактической ширины не означает автоматической записи нового пользовательского запроса.

`content[i]` не равняется длине строки или ширине только одного видимого body-cell. При выборе способа измерения необходимо учитывать заголовок, controls, отступы, шрифты и содержимое строк. Область измерений при виртуализации требует решения по пункту O4.

## 3. Инварианты

### 3.1. Размеры поверхности

- Контейнер Table занимает всю доступную ширину родителя.
- Высота определяется заголовком, данными, раскрытыми строками и остальными элементами Table. Фиксированная внутренняя высота и внутренний вертикальный viewport не должны быть обязательными.
- Добавление строк увеличивает логическую высоту. Виртуализация не должна требовать одновременного DOM-рендера всех строк.
- Строки могут иметь разную высоту, определяемую содержимым. Одинаковая или заранее фиксированная высота не является условием включения виртуализации.
- Сумма фактических ширин колонок всегда не меньше доступной ширины контейнера. Сужение останавливается на границе заполнения. Невыполнимая конфигурация верхних пределов отклоняется; свободный остаток справа не отображается.
- Если нижние ограничения не позволяют поместить колонки, появляется горизонтальное переполнение.

### 3.2. Типы колонок

- В непустой активной конфигурации должна оставаться хотя бы одна auto-колонка.
- Единственная колонка обязана быть auto.
- Из двух колонок fixed может быть максимум одна.
- Ручное расширение auto не преобразует её в fixed.
- Даже если вручную расширены все auto, их автоматическая база сохраняется.
- Схема без колонок или без видимой auto-колонки отклоняется как ошибочная. Пустой набор строк при корректной схеме отображает предусмотренное пустое состояние.

### 3.3. Содержимое и ограничения

- Содержимое, не помещающееся в выделенную auto-ширину, не должно само раздвигать геометрию таблицы сверх этой ширины.
- Способ отображения не поместившегося содержимого определяется контрактом ячейки; это не основание увеличивать `T`.
- Нижние и верхние ограничения применяются до фиксации результата resize.
- `min[i] > max[i]` является ошибкой конфигурации.
- При нехватке места нельзя получать отрицательные ширины.

## 4. Опорная раскладка и контентный предел

Опорная раскладка формируется при наличии измеримой доступной ширины. Нулевая ширина скрытого контейнера не должна становиться опорным размером.

Для auto-колонки нижний предел определяется следующим образом:

```text
floor[i] = max(min[i], min(content[i], reference[i]))
```

`reference[i]` предварительно должен удовлетворять явным `min/max`.

Пример: при `W = 1000`, `F = 400` единственная auto получает `reference = 600`.

| Потребность содержимого | reference | floor при отсутствии дополнительного min |
| ----------------------: | --------: | ---------------------------------------: |
|                     200 |       600 |                                      200 |
|                     600 |       600 |                                      600 |
|                     800 |       600 |                                      600 |

Последняя строка означает: первоначально длинное содержимое ограничено выделенными 600 единицами шкалы `numbers`; последующее уменьшение контейнера не позволяет сжать колонку ниже этой ширины.

Изменение окна само по себе не переписывает опорный размер, контентный предел или ручной запрос. Иначе расширение окна может необратимо повышать минимум, а сужение — стирать его.

Срок жизни опорной раскладки и её обновление при смене данных или схемы определяются в O2. До этого решения опорные размеры нельзя незаметно пересоздавать на каждом render, resize или mount виртуализированной ячейки.

## 5. Автоматическая раскладка при изменении контейнера

Этот раздел описывает автоматическую раскладку. Его формулы нельзя безусловно запускать вместо направленной операции ручного resize из раздела 7.

### 5.1. Единственная auto

Без верхнего ограничения:

```text
base  = max(floor, W - F)
width = max(base, manual), если manual есть
width = base, если manual отсутствует
T     = F + width
overflow = max(0, T - W)
```

При наличии совместимого верхнего ограничения:

```text
base  = clamp(W - F, floor, maxWidth)
width = min(maxWidth, max(base, manual)), если manual есть
```

Если `F + maxWidth < W`, заполнить контейнер при соблюдении максимума невозможно. Применяется решение O3, а не скрытое нарушение одного из ограничений.

### 5.2. Несколько auto

Ручные расширения не должны участвовать в расчёте автоматических долей других auto. Сначала вычисляются `base[i]`, затем накладываются `manual[i]`:

```text
width[i] = min(max[i], max(base[i], manual[i]))
```

Для отсутствующего `manual[i]` используется только `base[i]`.

Предлагаемый способ автоматического распределения:

```text
R = W - F
base[i] = clamp(lambda * weight[i], floor[i], max[i])
```

`lambda` подбирается так, чтобы сумма `base[i]` равнялась `R`, если ограничения это допускают. При равных весах колонки, не упёршиеся в ограничения, получают равные ширины.

Если `R < sum(floor[i])`, используются нижние пределы и возникает переполнение. Если `R > sum(max[i])`, совместное выполнение заполнения и верхних ограничений невозможно.

Равные веса являются предложением для распределения, а не уже согласованным публичным API. Выбор исходных долей фиксируется по O5.

### 5.3. Сохранение пользовательского запроса

При `F = 400`, `floor = 200`, `manual = 700`:

| Последовательность |    W | base | width | overflow |
| ------------------ | ---: | ---: | ----: | -------: |
| Исходный размер    | 1000 |  600 |   700 |      100 |
| Окно расширили     | 1200 |  800 |   800 |        0 |
| Окно вернули       | 1000 |  600 |   700 |      100 |
| Окно уменьшили     |  800 |  400 |   700 |      300 |

Автоматический рост фактической ширины до 800 не записывает `manual = 800`.

## 6. Ручное изменение auto

- Ручка расположена справа.
- Левая граница активной auto неподвижна; правая следует за указателем в пределах допустимого диапазона.
- Ручное сужение не должно уменьшать колонку ниже её собственной текущей автоматической ширины `base`.
- Ни расширение, ни обратное сужение ручного расширения auto не должны перераспределять ширины других auto.
- Если таблица заполняла контейнер, расширение auto сверх `base` увеличивает `T` и создаёт горизонтальное переполнение.
- Колонки справа сдвигаются вслед за новой правой границей; их ширины остаются прежними.

Для неизменного контейнера во время операции:

```text
target = clamp(widthAtDragStart + pointerDeltaX, base, maxWidth)
```

Требуемый переход состояния при явном ручном возврате к автоматической границе:

```text
если target достиг base:
    удалить manual
иначе:
    manual = target
```

Это правило снимает пользовательское расширение. Сохранение самого `base` в `manual` создало бы ложный минимум после следующего уменьшения окна. Простое нажатие без перетаскивания не должно сбрасывать настройку.

Если окно расширилось так, что `base >= manual`, запрос сохраняется до явного ручного возврата или отдельной операции сброса. Само изменение окна его не удаляет.

## 7. Направленный resize fixed с правой стороны

Resize доступен только для колонки с явным `resizable={true}`. Отсутствующее значение и `false` запрещают захват и скрывают ручку. У последней активной колонки разрешение игнорируется при любом значении.

### 7.1. Общие правила

1. Ручка всегда находится справа от изменяемого столбца.
2. Левая граница активного столбца остаётся на месте.
3. Правая граница следует за указателем до достижения допустимых ограничений.
4. Ширины и координаты колонок слева не меняются из-за этого drag.
5. Компенсировать изменение ширины могут только auto-колонки справа от активного столбца.
6. Fixed-колонки справа сохраняют ширины и сдвигаются при необходимости.
7. После отпускания указателя геометрия не должна перескакивать вследствие повторного глобального распределения.

### 7.2. Расширение

Пусть `d >= 0` — допустимое увеличение active fixed. Для каждого auto справа существует доступный запас сжатия до его действующего нижнего ограничения. Если у него есть ручной запрос, компенсация не должна стирать этот запрос или сжимать колонку ниже него.

Для состояния без незаполненной области:

```text
Cright = суммарный допустимый запас сжатия auto справа
compensation = min(d, Cright)
Tnew = Told + d - compensation
```

Распределение компенсации между несколькими auto справа должно использовать выбранную политику долей и ограничения каждой колонки. Auto слева в эту сумму не входят.

Когда запас справа исчерпан, дальнейшее увеличение активной колонки увеличивает `T` и горизонтальное переполнение.

### 7.3. Последний столбец

У крайнего правого столбца всей активной схемы нет ручки resize. Это правило не зависит от виртуализации: последняя смонтированная колонка окна сохраняет ручку, если справа существуют другие активные колонки.

Остальные ручки содержат два независимых индикатора: левый и правый. Зелёный показывает разрешённое движение в свою сторону, серый — достигнутый предел. Состояние индикатора рассчитывается из тех же ограничений, что и операция resize, и обновляется во время drag и изменения контейнера.

Прежний сценарий прямого resize последней fixed отменён этим уточнением пользователя.

### 7.4. Обратное сужение fixed

Если справа есть auto, освободившееся пространство может заполняться ими в пределах ограничений. Сначала должно уменьшаться существующее переполнение; расширение auto для заполнения требуется только при появлении незанятого места.

Для допустимого отрицательного изменения `d`:

```text
TwithoutCompensation = Told + d
requiredFill = max(0, W - TwithoutCompensation)
growth = min(requiredFill, доступный запас расширения auto справа)
Tnew = TwithoutCompensation + growth
```

Сужение ограничивается существующим overflow и запасом расширения auto справа. Если они исчерпаны, активная граница останавливается. Результат `Tnew < W` запрещён.

### 7.5. Состояние после drag

Для направленного resize недостаточно сохранить только новую fixed-ширину и заново применить формулу `W - F` ко всем auto: это может изменить колонки слева и отменить результат операции.

Результат направленной раскладки должен быть представлен в состоянии движка. Способ его хранения не предписывается. Переход к последующему resize контейнера необходимо определить по O6 и проверить отдельной последовательностью событий.

## 8. Изменение контейнера и жизненный цикл операции

- Resize контейнера является отдельной операцией и может перераспределять автоматические ширины по всей таблице.
- Он не должен автоматически переписывать пользовательские запросы, опорные размеры и контентные пределы.
- При изменении контейнера во время drag границы и точка отсчёта указателя пересчитываются без скачка.
- Обработка горизонтального скролла во время drag должна использовать координаты содержимого, а не смешивать их с координатами окна.
- При достижении min/max разделитель останавливается на границе; обратное движение не должно требовать проходить накопленное за ограничением расстояние.
- Отмена операции восстанавливает её пользовательские изменения, сохраняя актуальную внешнюю ширину контейнера.
- Обновление данных или схемы во время drag должно иметь явную политику продолжения либо отмены операции.

## 9. Координаты, виртуализация и программное закрепление хедера

### 9.1. Общая геометрия

Геометрия является общей для заголовка, body, закреплённых областей и служебных строк.

Для обычного порядка колонок:

```text
x[0] = 0
x[i] = sum(width[j]), где j < i
T = sum(width[i])
overflow = max(0, T - W)
```

Для строк:

```text
y[row] = headerHeight + сумма высот предшествующих строк
contentHeight = headerHeight + сумма высот всех логических строк
```

Высота поверхности дополнительно учитывает её отступы, границы и место scrollbar, если он участвует в потоке. Изменение ширины может менять переносы содержимого и высоты строк.

### 9.2. Виртуализация

Виртуализация должна:

- Отбирать видимые строки и колонки по общей геометрии и viewport с overscan.
- Работать при внешнем вертикальном скролле и естественной высоте таблицы.
- Сохранять логические размеры не отрисованных областей.
- Не сбрасывать размеры и пользовательские запросы при unmount ячеек.
- Не требовать знания ширины через измерение каждого DOM-cell на каждом scroll.
- Поддерживать реальные высоты раскрытых и многострочных строк через оценки для неизмеренных областей, фактические измерения и последующую корректировку геометрии и скролла.
- Сохранять соответствие header/body и корректность закрепления при resize.

Фиксированные или известные заранее высоты допускаются как частный упрощённый режим. Основной контракт не должен требовать их от потребителя.

#### 9.2.1. Оценки и измерения высот

Для каждой логической строки используется актуальная измеренная высота либо оценка:

```text
height[i] = measuredHeight[i], если измерение актуально
height[i] = estimatedHeight[i], если актуального измерения нет

offset[0] = 0
offset[i] = sum(height[j]), где j < i
bodyHeight = sum(height[i])
```

По накопленным высотам core определяет диапазон строк, пересекающий viewport и overscan. Верхняя и нижняя пустые области либо другой выбранный механизм размещения сохраняют полную текущую логическую высоту body, включая не отрисованные строки.

После отображения runtime получает фактические размеры и приводит их из CSS px к единицам `numbers`. Изменения размеров вследствие переносов, изображений, асинхронного содержимого или шрифтов должны повторно обновлять измерение.

Измерения хранятся по стабильной identity логической строки и версии геометрии/содержимого. Индекс строки в текущем массиве не является достаточным ключом. Выход строки из DOM не должен удалять её актуальное измерение.

При изменении ширин колонок, содержимого или типографики затронутые измерения признаются устаревшими. Повторное измерение не должно блокировать отображение всей таблицы: до уточнения используется обозначенная как оценочная высота.

#### 9.2.2. Корректировка скролла по видимой строке

До применения пакета изменённых высот runtime определяет опорную видимую строку и положение viewport внутри неё. Overscan-строка выше видимой области не выбирается в качестве такой опоры. Учитываются перекрывающий закреплённый хедер и актуальные внешние отступы viewport.

После пересчёта core возвращает новую геометрию, а runtime корректирует выбранный scroll owner так, чтобы сохранить ту же видимую строку и смещение внутри неё. Для неизменного смещения внутри опорной строки:

```text
deltaScroll = newAnchorPosition - oldAnchorPosition
newScrollTop = oldScrollTop + deltaScroll
```

Позиции опоры и scroll должны быть выражены в одной системе координат. При записи в браузер логическая корректировка преобразуется в CSS px и ограничивается допустимым диапазоном scroll owner.

- Если изменилась высота строк выше опоры, корректируется scroll, чтобы видимое содержимое не сдвинулось.
- Изменение высот только ниже опоры само по себе не должно двигать viewport.
- Если изменилась сама опорная строка, сохраняется допустимое смещение внутри неё; оно не может указывать за её новую нижнюю границу.
- Если опорная строка удалена или скрыта, выбирается ближайшая сохранившаяся строка в прежнем порядке: сначала следующая, затем предыдущая; при отсутствии строк используется допустимое пустое состояние.
- Коррекция должна опираться на актуальный viewport и не возвращать пользователя к позиции, сохранённой до его нового действия прокрутки.
- Несколько измерений применяются согласованным пакетом, без последовательного видимого перемещения viewport после каждой ячейки.
- Нативное scroll anchoring и корректировка runtime должны быть согласованы, чтобы изменение высоты не компенсировалось дважды.
- Если таблица не участвует в видимой области, её корректировка не должна перехватывать прокрутку другого содержимого страницы.

Уточнение оценок может менять полную высоту таблицы и размер scrollbar. Гарантия сохранения видимого содержимого не означает, что точная полная высота известна до измерения всех необходимых областей.

#### 9.2.3. Совместная виртуализация строк и колонок

Высота строки зависит от её ячеек, включая колонки, которых сейчас нет в DOM. Нельзя объявлять измерение только видимых ячеек точным измерением всей строки.

Для актуальной версии ширин и содержимого необходимо сохранять уже известные высоты ячеек или эквивалентную информацию, достаточную для определения высоты строки. Горизонтальный unmount высокой ячейки не должен сам по себе уменьшать строку.

Если вновь отображённая колонка содержит более высокую ячейку, измерение уточняет высоту строки, после чего применяются общие правила пересчёта и сохранения опоры viewport. При неполном покрытии колонок высота остаётся уточняемой оценкой.

Инвалидация при реальном изменении содержимого или ширины должна позволять высоте уменьшаться. Запрет на уменьшение при одном только unmount не должен превращаться в пожизненное сохранение максимальной когда-либо наблюдавшейся высоты.

Header, body, закреплённые колонки и expanded lines используют согласованную высоту каждой логической строки. Программное закрепление хедера получает полную актуальную логическую высоту таблицы, а не границу последней смонтированной строки.

#### 9.2.4. Ответственность слоёв

- Core принимает текущие высоты и их изменения, рассчитывает накопленные координаты, видимый диапазон, размеры пропущенных областей и положение опорной строки.
- Runtime владеет измерениями и их актуальностью, viewport и опорой, получает изменения размеров, вызывает core и применяет согласованную корректировку scroll owner.
- View отображает выбранное окно строк и ячеек, сохраняет логическое место не отрисованных областей и предоставляет элементы для измерения. Требование одинаковой высоты не закладывается в React-представление.

Оценки высот не являются точными контентными пределами колонок и не должны автоматически переписывать `reference` или `floor` ширин. Правила измерения контентной ширины остаются предметом O4.

### 9.3. Программное закрепление хедера

Выбранный механизм — закрепление под управлением runtime. Поддерживаются обычное отображение без закрепления и программное закрепление относительно выбранного вертикального scroll owner. Для естественной высоты таблицы scroll owner может быть страницей либо внешней прокручиваемой панелью; внутренний viewport фиксированной высоты не является обязательным.

Runtime получает положение таблицы и хедера, высоту хедера, положение viewport и актуальный верхний отступ. Core получает эти данные в единой системе координат и определяет смещение. View применяет рассчитанное положение с использованием принятого контракта токенов.

Положение хедера ограничивается самой таблицей:

- До достижения порога хедер находится на обычном месте.
- При достижении порога хедер удерживается у верхнего края viewport с заданным отступом.
- При достижении конца таблицы хедер уходит вместе с ней и не остаётся поверх следующего содержимого страницы.
- Если высоты таблицы недостаточно для перемещения хедера, он не получает дополнительного свободного хода.

Для вертикального закрепления сверху после нормализации координат:

```text
headerTop = исходная позиция хедера в координатах содержимого scroll owner
tableBottom = нижняя граница таблицы в тех же координатах
scrollTop = положение вертикального scroll owner
topOffset = отступ от верхней границы его viewport
headerHeight = актуальная высота всего хедера

desiredShift = scrollTop + topOffset - headerTop
maxShift = max(0, tableBottom - headerTop - headerHeight)
headerShift = clamp(desiredShift, 0, maxShift)
renderedHeaderTop = headerTop + headerShift - scrollTop
```

`topOffset` может учитывать шапку приложения и другие закреплённые панели, в том числе при изменении их высоты. Механизм передачи этой величины должен сохранять совместимость публичного API; новые props здесь не назначаются.

Границы ответственности:

- Core рассчитывает смещение и состояние хедера: обычное, закреплённое или уходящее у конца таблицы.
- Runtime отслеживает выбранный scroll owner, scroll/resize и изменения размеров, нормализует измерения и обновляет snapshot. Получение геометрии не должно требовать чтения всех ячеек на каждом scroll.
- View применяет позицию, clipping и порядок наложения. Зависимости от DOM и конкретного способа позиционирования не попадают в core.

Header и body используют одну геометрию колонок и один рассчитанный шаблон. Горизонтальное положение хедера синхронизируется с body, включая виртуализированные и закреплённые колонки. Программное вертикальное закрепление не должно менять размеры колонок или создавать независимое состояние горизонтального скролла.

Исходное место хедера в вертикальной геометрии сохраняется, поэтому переход к закреплённому отображению не сдвигает строки. Высота хедера измеряется заново при переносах, нескольких уровнях заголовков или изменении controls.

Должен существовать единственный интерактивный React-хедер. Переходы между состояниями не должны терять фокус, локальное состояние controls, активную операцию resize или создавать вторую доступную для взаимодействия копию заголовков.

Программное смещение само по себе не отменяет clipping и stacking context предков. Если выбранная структура требует другого слоя размещения, view может использовать portal или отдельную поверхность. Это деталь размещения; расчёт core и состояние runtime от неё не зависят. Использование portal не отменяет требования к единственному хедеру и сохранению его состояния.

| A39 | Изменились высота хедера либо topOffset                                                         | Ограничения пересчитаны, сохранено место в потоке; нет ошибочного выхода за таблицу                                         |
| A40 | На странице несколько таблиц или короткая таблица                                               | Каждая ограничивает свой хедер своими границами; отсутствует закрепление поверх чужого содержимого                          |

| A42 | Состояние закрепления меняется во время drag                                                    | Активная операция и координаты указателя не теряются; геометрия не прыгает                                                  |
| A43 | Предки ограничивают отображение хедера                                                          | Выбранный view-слой учитывает clipping и stacking; при необходимости другая поверхность не меняет правила core              |
| A44 | Проверяется разделение слоёв                                                                    | Расчёты core выполняются без React/DOM; runtime управляет событиями и состоянием, view отображает snapshot                  |

A14–A16 и переход из направленного resize к resize контейнера проверяются отдельно от формул глобальной автоматической раскладки. Предыдущая численная модель глобального распределения не подтверждает эти новые сценарии.

Сценарии O1–O6 должны получить ожидаемые результаты до реализации соответствующих переходов. Их нельзя считать принятыми по одному факту существования формул в этом документе.

## 11. Требования к проверке реализации

1. Проверить арифметические инварианты: ограничения размеров, суммы, координаты и величину переполнения.
2. Проверить последовательности событий: окно уменьшили и вернули; auto расширили и вернули к base; fixed изменили справа, завершили drag, затем изменили контейнер.
3. Проверить порядок колонок: auto только справа, только слева, с обеих сторон и отсутствие auto справа от последней колонки.
4. Проверить взаимодействия в браузере с реальными React-ячейками, включая выделение, controls, закрепление и изменяемую высоту.
5. Проверять производительность в production-сборке на согласованной нагрузке. Измерять время кадров, задержку resize, объём DOM и память; размер массива данных сам по себе не является показателем скорости.
6. Проверить, что стоимость отображения ограничена viewport и overscan, а не полным числом ячеек.
7. Выбрать worker или дополнительные механизмы ускорения только после установления нагрузки и стоимости расчётов. Проверка геометрии не является доказательством ускорения.
8. Проверить программное закрепление при внешнем scroll owner, динамических topOffset/headerHeight, горизонтальном скролле, виртуализации, закреплённых колонках и активном resize.
9. Проверить адаптивные темы numbers, преобразование измерений, валидность токенов и сохранение общей ширины при дробных результатах.
10. Отдельно проверять core на обычных данных, runtime на последовательностях событий и view на реальном браузерном поведении. Логика расчёта не должна дублироваться в слоях.
11. Проверить строки динамической высоты: уточнение оценок выше и ниже viewport, изменение самой опорной строки, horizontal unmount высокой ячейки, изменение ширины и содержимого, асинхронные размеры, удаление опоры и совместную работу с нативным scroll anchoring.

Числовые бюджеты производительности и целевые устройства согласовываются на этапе прототипа. ТЗ не утверждает неподтверждённую гарантию FPS.

## 12. Решения, необходимые для завершения контракта

### O1. Граница заполнения — решение принято

Сумма ширин не меньше ширины контейнера. Сужение прекращается после исчерпания overflow и запаса роста auto справа. Последняя колонка всей активной схемы не имеет resize-ручки.

### O2. Срок жизни reference и floor

Необходимо определить поведение при смене данных, загрузке новых строк, изменении содержимого, шрифтов, видимости и набора колонок, повторном открытии таблицы и явном сбросе размеров.

Открытие таблицы сразу при W=800 и уменьшение уже открытой таблицы с W=1000 до W=800 могут давать разные результаты при длинном содержимом. Нужно явно решить, допустима ли такая зависимость от истории и какие операции начинают новую опорную раскладку.

### O3. Верхние пределы и обязательное заполнение

Если `F + sum(maxAuto) < W`, заполнить контейнер без нарушения max невозможно. Для произвольно растущего контейнера гарантировать заполнение можно при наличии хотя бы одной auto без жёсткого верхнего предела. Альтернативное поведение для незаполненного остатка требует отдельного решения.

### O4. Определение контентной потребности

Необходимо выбрать правила переноса, ограничения содержимого и область измерений: все строки, доступные измеренные строки или оценка. Отдельно определить обновление измерений при виртуализации, изображениях, асинхронном содержимом и смене шрифтов.

Нельзя обещать точный максимум по всем строкам, если измерены только видимые ячейки.

### O5. Доли нескольких auto

Нужно закрепить способ первоначального распределения и компенсации справа: равные ширины свободных колонок, пропорции или другой алгоритм. Ограничения каждой колонки должны соблюдаться при любом выбранном способе.

### O6. Resize контейнера после направленного resize

Исторический пример resize последней колонки больше недоступен в UI. Вопрос сохраняется для внутренних fixed: например, `[auto 400][fixed 200][auto 400]` с floor auto 100 после увеличения средней fixed до 700 даёт `[auto 400][fixed 700][auto 100]`, T=1200.

Нужно определить результаты последующих W=900, W=1001 и W=1200, включая обратное возвращение к W=1000. Наивный глобальный расчёт способен изменить auto слева уже при прежнем W и отменить направленный результат.

Согласованное решение должно различать автоматическую базу, результат направленной операции и пользовательские запросы; не создавать произвольного нового контентного минимума для auto слева; не вызывать скачок только из-за смены обработчика события.

## 13. Результат будущей реализации

Результатом должен стать совместимый React-компонент Table с архитектурой core/runtime/view, собственной геометрией, размещением колонок через рассчитанные токены CSS Grid, правым направленным resize, программным закреплением хедера, предсказуемым горизонтальным переполнением и виртуализацией динамических строк с измерениями и корректировкой скролла. Формулы и переходы состояния должны быть покрыты сценариями приёмки, а взаимодействия — проверены в браузере.

Текущий документ является основанием для завершения контракта и подготовки прототипа. Открытые решения O1–O6 не дают разрешения выбрать произвольное поведение или начать миграцию потребителей без отдельного запроса на реализацию.
